## 1. 架构目标与约束

### 1.1 质量属性驱动

| 驱动因素 | 来源 | 架构上的回应 |
| --- | --- | --- |
| 操作跟手，不能被 RTT 拖慢 | NFR-1、2.4 | 客户端预测 + 按键即起步；服务端权威兜底 |
| 所有人看到同一局 | NFR-2、FR-5.6 | 单一权威模拟 + 全量快照 + 增量地图 |
| 远端移动要连续 | NFR-1、FR-5.5 | 90ms 延迟回放 + 样本间线性插值 |
| 单人也能玩 | G3、FR-4 | AI 作为普通输入源，无特权、不占连接 |
| 一台机器、零构建即可跑 | NFR-10、G5 | Node 单进程 + 原生前端 + 仅 `ws` 一个依赖 |
| 从 320px 到 1920px 都能玩 | NFR-4、FR-8 | 运行时求解棋盘尺寸 + 断点/能力查询 |
| 规则可测、可调 | NFR-6 | 逻辑与网络解耦、纯函数阵容规划、常量集中 |

### 1.2 约束

| 约束 | 说明 | 影响 |
| --- | --- | --- |
| 单进程 | 当前部署模型 | 房间状态在内存；多进程需按房间号分片 |
| 无数据库 | 定位为轻量休闲服务 | 重启丢局；无战绩 |
| JSON over WebSocket | 调试友好、零编解码依赖 | 带宽高于二进制；靠状态最小化控制 |
| 浏览器无构建 | 直接 `<script>` 加载 | 模块通过全局对象协作，需自律依赖方向 |
| 单房间 ≤ 4 人 | 玩法与性能共同决定 | 广播可全量、无需 AOI |

### 1.3 架构风格

- **客户端/服务端（C/S）**，服务端权威（Authoritative Server）。
- **分层 + 事件驱动**：网络层只做接入与转发，模拟层只做规则，表现层只做渲染。
- **内存态有状态服务**：房间即聚合根，生命周期由连接与定时器驱动。
- **同构内核**：移动推进与插值算法抽成 `motion.js`，浏览器与 Node 共用同一份实现。

## 2. 系统总览

### 2.1 系统上下文

```
        ┌──────────────────────┐        HTTP GET /index.html /js/*.js /style.css
        │   浏览器玩家 1..4/房  │ ─────────────────────────────────────────────┐
        │  Canvas + DOM + WS   │ ◀────────────── 静态资源 ────────────────────┤
        └──────────┬───────────┘                                              │
                   │ WebSocket（JSON）                                        ▼
                   │  上行：hello / create / quick / join / ready /      ┌─────────────────────────┐
                   │        start / input / leave / ping                │  Node.js 单进程          │
                   │  下行：room / game / state / over / err / ...      │  ┌───────────────────┐  │
        ┌──────────┴───────────┐                                          │  │ HTTP 静态服务      │  │
        │   浏览器玩家 2..4    │ ◀───────────────────────────────────────▶│  ├───────────────────┤  │
        └──────────────────────┘                                          │  │ WS 接入 / 会话     │  │
                                                                          │  ├───────────────────┤  │
                                                                          │  │ 房间 + 匹配        │  │
                                                                          │  ├───────────────────┤  │
                                                                          │  │ Game 50Hz 模拟     │  │
                                                                          │  │ Bot / Lineup       │  │
                                                                          │  └───────────────────┘  │
                                                                          └─────────────────────────┘
```

外部依赖只有 Node.js 标准库与 `ws`；无第三方服务、无 CDN、无数据库。

### 2.2 分层视图

```
┌─────────────────────────────────────────────────────────────┐
│ 表现层  index.html / style.css / render.js / main.js        │
│         界面状态机、HUD、Canvas 绘制、输入采集、音效          │
├─────────────────────────────────────────────────────────────┤
│ 适配层  layout.js（尺寸求解/断点）  motion.js（移动/插值）    │
│         把"屏幕与时间"翻译成表现层能直接用的量                │
├─────────────────────────────────────────────────────────────┤
│ 传输层  net.js（WebSocket 封装、重连、RTT、消息分发）         │
├─────────────────────────────────────────────────────────────┤
│ 接入层  index.js：HTTP 静态 + WS 握手 + 心跳 + 消息路由       │
├─────────────────────────────────────────────────────────────┤
│ 会话层  sessions / clients / Room / 匹配 / 重连宽限 / 结算    │
├─────────────────────────────────────────────────────────────┤
│ 模拟层  game.js（规则与状态）  bot.js（AI 输入源）            │
│         lineup.js（人数校验与队伍分配，纯函数）               │
└─────────────────────────────────────────────────────────────┘
```

依赖方向严格向下：表现层不直接碰 `ws`，模拟层不依赖网络与 DOM。

### 2.3 运行时视图

| 运行单元 | 数量 | 职责 | 生命周期 |
| --- | --- | --- | --- |
| HTTP Server | 1 | 静态资源、`/health` | 进程级 |
| WebSocketServer | 1 | 连接、握手、消息路由 | 进程级 |
| 心跳定时器 | 1（30s） | 清理僵死连接 | 进程级 |
| Room | 0..N | 房间配置、真人/AI 席位、对局 | 首个玩家加入 → 无真人时销毁 |
| 房间模拟定时器 | 每房 1（20ms） | 调用 `game.tick()` 并广播 | 开局创建 → 对局结束清除 |
| 自动开局定时器 | 每房 0..1（12s） | 混合快速房到点开局 | 触发或手动开局后清除 |
| 断线宽限定时器 | 每断线玩家 1（12s） | 超时判负并移出 | 断线时创建，重连/移出时清除 |
| 浏览器渲染循环 | 每客户端 1（rAF） | 预测、插值、绘制、HUD | 页面生命周期 |

Node 单线程事件循环：所有房间的 `tick`、消息处理、广播串行执行。单房间 4 人时单 tick 工作量很小，房间数增加时表现为定时器数量线性增长（见 11 节技术债）。

### 2.4 部署视图

```
┌──────────────── 单台主机 / 单个 Node 进程 ────────────────┐
│  process.env.PORT (默认 3000)                             │
│  process.env.HOST (默认 0.0.0.0)                          │
│  ├─ GET /            → public/index.html                  │
│  ├─ GET /js/*.js     → public/js/*（no-cache）            │
│  ├─ GET /style.css   → public/style.css                   │
│  ├─ GET /health      → { ok, rooms, uptime }              │
│  └─ WS  /            → 同端口升级                          │
│                                                           │
│  静态资源目录：public/（路径穿越已拦截）                    │
│  无构建产物、无反向代理依赖、无外部存储                     │
└───────────────────────────────────────────────────────────┘
```

同一局域网的手机访问 `http://<内网IP>:3000` 即可；公网部署只需把端口暴露出去（NAT 穿透不在范围内，见需求 R-5/A-3）。

## 3. 模块划分

### 3.1 服务端

| 模块 | 路径 | 职责 | 对外接口 | 依赖 | 对应需求 |
| --- | --- | --- | --- | --- | --- |
| 规则与状态 | `server/game.js` | 地图生成、移动、炸弹、爆炸、箱子/道具、泡封/挣扎/补刀/救援、计时、胜负、快照与地图载荷 | `new Game({players, seed, teamMode})`、`setInput(id,msg)`、`tick()`、`snapshot()`、`mapPayload()`、`blastPreview()`、`canEnter()`、`moveDuration()`、`setOnline()`、`forceEliminate()` | 仅 `bot.js`（创建控制器） | FR-3.*、FR-5.6、NFR-2 |
| AI 控制器 | `server/bot.js` | 危险图、时间感知 BFS 逃生、放弹收益与逃生验证、目标选择、挣扎 | `new Bot({game,id,difficulty,seed})`、`think(now)`、`onArrive()` | `game` 的公共方法（只读 + `setInput`） | FR-4.* |
| 阵容规划 | `server/lineup.js` | 配置归一化、人数校验、真人席位、队伍与出生角分配、AI 名单/队名 | `normalizeConfig()`、`humanCapacity()`、`validateLineup()`、`planLineup()`、`VALID_LINEUPS` | 无（纯函数） | FR-1.*、FR-2.5、FR-2.8 |
| 校验与限流 | `server/validate.js` | 昵称/房号/聊天文本清洗（Unicode 码点截断）、id/seq/dir 白名单、令牌桶 | `sanitizeName()`、`normalizeCode()`、`normalizeChat()`、`normalizeId()`、`normalizeSeq()`、`isValidDir()`、`createBucket()` | 无（纯函数，v1.1 新增） | FR-15.1、FR-15.3、FR-11.3 |
| 网络与房间 | `server/index.js` | HTTP 静态、WS 握手/路由、房间生命周期、匹配、广播、重连宽限、心跳、结算、聊天广播、限流与加固 | 内部：`Room.start/step/finish`、`createRoom/joinRoom/leaveRoom`；导出 `server`、`rooms` | `http`、`fs`、`path`、`ws`、`game`、`lineup`、`validate` | FR-2.*、FR-5.*、FR-10.*、FR-11.1、FR-15.* |

**边界约束**

- `game.js` 不 `require('ws')`、不读 `req/res`、不 `setInterval`——循环由外部驱动，因此可单测。**v1.1 对其零改动。**
- `bot.js` 只能通过 `game.setInput()` 改变世界；读取危险图时只调用 `blastPreview()` 等只读方法（FR-4.1）。**v1.1 对其零改动。**
- `lineup.js` 不接触 `Game` 实例，只做数组与整数运算。
- `validate.js` 是纯函数模块：不持有连接、不碰定时器，可被任何入口（WS / 未来的 HTTP）复用。

### 3.3 依赖关系与分层约束

```
                    ┌──────────────┐
                    │  main.js     │  唯一的状态编排者（接线 Chat/Share/Panels/Store）
                    └──┬──┬──┬──┬──┘
          ┌────────────┘  │  │  └─────────────┐
          ▼               ▼  ▼               ▼
     ┌────────┐    ┌──────────┐ ┌──────────┐ ┌─────────┐
     │ net.js │    │motion.js │ │layout.js │ │panels.js│──▶ store.js（注入 storage）
     └────────┘    └──────────┘ └──────────┘ └─────────┘
          ▲               ▲              │
          │               │              ▼
          │        ┌──────────┐    ┌──────────┐
          └───────▶│ render.js│◀───│ style.css│
                   └──────────┘    └──────────┘
     chat.js / share.js ──▶ 仅依赖注入的 Net.send / History / Clipboard，
                            不与 render/layout 交互

        server/index.js ──▶ server/game.js ──▶ server/bot.js
                │                  ▲
                ├─▶ server/lineup.js（无反向依赖）
                └─▶ server/validate.js（纯函数，被消息入口逐条调用）
```

| 规则 | 说明 |
| --- | --- |
| 服务端单向 | `index → game → bot`；`lineup`、`validate` 被 `index` 使用，不反向依赖任何模块 |
| 客户端单向 | `main` 可调用其余模块；`render` 只接收 `scene` 数据；`chat/share/panels/store` 互相不引用，全部通过 `main.js` 注入依赖 |
| 同构模块 | `motion.js`、`store.js` 不引用 `window`/`document`（`store` 的 storage 由外部注入），可在 Node 单测中直接 `require` |
| 无循环依赖 | `bot` 只持有 `game` 引用并调用其公共方法，`game` 只在构造时 `require` `bot` |

## 4. 关键技术选型

| 领域 | 选型 | 理由 | 备选与代价 |
| --- | --- | --- | --- |
| 运行时 | Node.js ≥ 18 | 与前端同语言、事件循环适合房间制 IO、零额外运行时 | Go/Java 性能更好但开发与部署更重 |
| 实时传输 | WebSocket + JSON（`ws`） | 全双工、浏览器原生、可读易调试、唯一依赖 | Socket.IO 功能多但体积/依赖大；二进制协议省带宽但调试成本高 |
| 前端框架 | 无（原生 DOM + Canvas） | 零构建、首屏快、无版本升级负担 | React/Vue 提升复杂 UI 开发效率，但引入构建链与体积 |
| 渲染 | Canvas 2D | 角色/炸弹/爆炸为程序化图形，2D 足够；可用离屏缓存 | WebGL 更强但复杂度与兼容成本高；DOM 精灵在大量绘制时更慢 |
| 音频 | WebAudio 合成 | 无需音频文件、无版权与加载问题 | 音频文件音质更好但增加资源与请求 |
| 同步模型 | 服务端权威 + 客户端预测 + 快照插值 | 反作弊与手感兼得，是实时对战的标准解法 | 纯权威手感差；客户端权威易作弊 |
| 模拟节奏 | 固定步长 50Hz，广播 16.7Hz | 规则稳定、带宽可控；渲染与模拟解耦 | 逐帧模拟受负载影响；广播更高则带宽上升 |
| 位置表示 | 整数格 + 连续坐标双表示 | 碰撞判定精确，广播/渲染平滑 | 纯浮点碰撞易穿模；纯格位渲染会跳格 |
| 随机 | `mulberry32(seed)` | 可复现、无依赖；地图与掉落可回放 | `Math.random` 不可复现，难排查 |
| 状态存储 | 进程内 `Map` / `Uint8Array` | 零运维、低延迟 | 重启丢局、难水平扩容 |
| 身份 | `sessionStorage` 客户端 id | 无账号即可区分标签页、支持重连 | 可伪造；换设备/清缓存即新身份 |
| 测试 | `node:assert` + Playwright-core（本机 Edge） | 逻辑零依赖；浏览器实测覆盖手感/视觉/响应式 | 引入 Jest/Vitest 提升报告能力但增加依赖 |
| 构建 | 无 | 改完刷新即生效，部署只需拷贝目录 | 无 Tree-shaking/压缩，资源体积偏大 |

## 5. 核心机制设计

### 5.1 权威模拟循环

每个房间一个 `setInterval(…, 20)`，`Room.step()` 调用 `Game.tick()`，再按策略广播：

```
每 20ms（50Hz）
  ├─ if (now < startAt) return            // 2.2s 倒计时
  ├─ for bot of bots: bot.think(now)      // AI 先提交输入意图
  ├─ for player of players:
  │    ├─ 推进移动（到格则结算到达）
  │    ├─ 未在移动 → tryStartMove(arriveAt || now)
  │    └─ 被困计时到 → 淘汰
  ├─ 炸弹引信到点 → detonate（递归连锁）
  ├─ 清理过期爆炸
  └─ 超时 → timeUp

每 3 个 tick（≈16.7Hz）或存在事件 → snapshot + broadcast
```

设计要点：

- **固定步长**让移动、引信、被困计时都以服务端时间为准，不受广播频率影响（FR-3、NFR-1）。
- **事件触发额外广播**：放弹、爆炸、拾取、被困、淘汰等立即推送，避免最多 60ms 的观感延迟。
- **快照即真相**：`snapshot()` 同时承担"广播载荷"和"地图增量清空"职责，调用后 `changes`/`events` 归零（FR-5.6）。
- **结束延迟 900ms**：先让客户端播完最后一帧，再发 `over` 结算，避免画面瞬切。

### 5.2 位置表示与移动内核

**双表示**：`cellX/cellY` 表示逻辑格，`px/py` 表示连续坐标；移动时记录 `fromX/fromY → toX/toY + moveStart + moveDur`。

服务端推进（`game.js`）：

```
if (moving) {
  t = (now - moveStart) / moveDur
  if (t >= 1) {
    arriveAt = moveStart + moveDur      // 精确到达时刻
    cellX = toX; cellY = toY; px = cellX; py = cellY
    onCellEnter(...)                    // 补刀/救援/拾取/AI 重规划
  } else {
    px = fromX + (toX - fromX) * t
  }
}
if (!moving) tryStartMove(p, arriveAt || now)   // 用到达时刻续接，不丢余量
```

客户端（`motion.js` 的 `advance`）做同样的事，但用 `performance.now()`。关键点是**下一格的起点用上一格的精确到达时刻**，而不是当前帧/rAF 时刻——否则每格丢掉"帧时间 − 剩余时间"的零头，60fps 下单格耗时会在 150–167ms 间抖动（NFR-1、FR-5.3）。

客户端在 `keydown` 里直接调 `kickLocal()`，不等下一帧；松键时把当前格走完再停，避免半格悬空。

### 5.3 同步管线

```
输入              预测                权威                   校正/插值             渲染
─────          ─────────         ─────────────          ──────────────        ─────
keydown  ──▶ 本地 Motion.advance ──┐
   │                               │  {seq,dir,bomb}
   └──────── sendInput ────────────┴──────────▶ Game.setInput
                                                     │
                                              50Hz tick
                                                     │
   快照 {players,bombs,changes,events,lastSeq} ◀─────┘ 16.7Hz
        │
        ├─ 自己：reconcile()
        │    ├─ 任一端 moving → 不校正，仅 >2.4 格硬吸附
        │    ├─ 静止且 dist < 0.34 → 保留残余偏移
        │    └─ 否则对齐逻辑格 + corrX/corrY 指数衰减（≈150ms）
        │
        └─ 他人：pushSample(最多12个) → smoothRemotes(now-90ms) → 线性插值/≤120ms 外推
                                                     │
                                                     ▼
                                            scene() → Render.draw()
```

**为什么这么定**

| 机制 | 解决的问题 | 代价 |
| --- | --- | --- |
| 按键即起步 + 本地预测 | 纯权威要等一个 RTT，50ms 就明显发涩 | 需要校正策略，极端情况下要硬吸附 |
| "有一端在动就不校正" | 预测本来该领先，硬拉会橡皮筋 | 短时误差被容忍（视觉上看不出来） |
| 偏移指数衰减 | 对齐逻辑格时避免位置跳变 | 校正期间渲染位置略偏 |
| 远端 90ms 回放 + 插值 | 16.7Hz 快照直接渲染会一跳一跳 | 远端比真实位置晚约 90ms |
| 120ms 外推 | 快照短暂断流时不至于卡住 | 长断流仍会静止，靠重连恢复 |
| 炸弹乐观渲染 + 800ms 兜底 | 放弹即时反馈 | 被拒时会出现短暂"幽灵炸弹" |

### 5.4 地图与爆炸

**地图生成**（FR-3.1）：外圈 `WALL`；内部 `x%2==0 && y%2==0` 为 `WALL`；其余 72% 为 `BOX`；随后清空四个出生点十字（只清内圈）与中心 3×3。

**爆炸**（FR-3.4）有两个入口，语义一致但用途不同：

| 入口 | 用途 | 是否改地图 | 连锁处理 |
| --- | --- | --- | --- |
| `blastPreview(x,y,power)` | AI 危险图、可行性验证 | 否（只读） | 炸弹视为可穿透，便于估算上游引爆 |
| `detonate(bomb)` | 真正引爆 | 是（炸箱、掉道具） | 同 tick 递归引爆队列 |

`detonate` 向四方向逐格推进：墙停；箱子 `destroyBox()` 后停；空格继续；遇到其他炸弹则加入 `chain` 并停止该方向，最后递归引爆。冲击格子统一做一次命中判定（`hitPlayerAt`），命中即 `trapPlayer`，不直接淘汰（FR-3.7）。

**道具掉落**（FR-3.5）：`rng() < 0.36` 才掉；再取随机数按 `0.40 / 0.38 / 0.22` 分成炸弹/火力/速度；地图变化写入 `changes:[x,y,item]`，客户端只改那一格。

### 5.5 阵容规划与匹配

```
normalizeConfig(msg)         // 模式白名单、bots 1..3、difficulty 1..3
      │
      ├─ pvp  → bots = 0，humanCapacity = 4
      ├─ pve  → humanCapacity = 1
      └─ hybrid → humanCapacity = 4 - bots
      │
planLineup({mode, humans, bots, teamMode})
      ├─ validateLineup() → 错误文案或 null
      ├─ useTeams = teamMode && total === 4
      ├─ 混战：FFA_SLOTS[total] → 对角/三角/四角
      └─ 分队：真人蛇形 → AI 补少人队 → TEAM_SLOTS 同侧出生
```

匹配只做一件事：遍历等待中的房间，找 `sameConfig()` 且 `players.size < humanCapacity` 的第一个并入，否则新建。`pve` 跳过匹配直接开局；`hybrid` 新建房后挂 12 秒自动开局（FR-2.2–2.4）。

### 5.6 AI 决策架构

```
think(now)
  ├─ 未到思考时刻 → return（间隔 = preset.think + rng*jitter）
  ├─ 被困 → struggle()
  ├─ 极小概率手滑 → 随机方向
  ├─ dangerMap()                     炸弹范围 + 挨炸时刻（连锁 +80ms）
  ├─ 当前/即将到达格在危险图 → findEscape()：时间预算 BFS，优先非死胡同
  ├─ 安全且站定 → maybeBomb()：收益评估 → 虚拟地图验证可逃 → 放弹并立刻转逃
  ├─ 否则 pickTarget()：道具 > 追敌 > 可炸箱开图
  └─ send({dir}) / send({bomb:true})   ← 与真人完全相同的入口
```

`onArrive()` 把 `nextThink` 置 0，使 AI 到格即重规划，避免"固定周期思考"导致的过冲或横跳（FR-4.5）。难度只调 `PRESET` 中的思考间隔、抖动、失误率、搜索深度、追击权重，不碰 `power/capacity/speed`（FR-4.6）。

### 5.7 布局求解

```
fit()
  ├─ 读 .stage 的 clientWidth/Height 与 padding
  ├─ 读 CSS 变量 --board-max（唯一尺寸真源，断点里写 560/680/700/780/880）
  ├─ w = min(可用宽 - HUD 占位, (可用高 - HUD 高 - gap) × 15/13, --board-max)
  ├─ 写入 --board-w（差值 <1px 不写）
  └─ 第二趟：HUD 换行改变高度 → 必要时重算
```

触发时机：`resize`、`orientationchange`（延后 120ms）、`visualViewport.resize`、`ResizeObserver`（stage/hud）、字体加载完成、界面切换、HUD 内容变化。所有触发经 rAF 合并，避免连续重排（FR-8.3、FR-8.7）。

### 5.8 连接生命周期与重连

```
连接 ──▶ hello {id,name}
          ├─ 同 id 旧连接存在 → close(4000, replaced)
          ├─ clients[id] = ws；sessions[id] 复用
          ├─ 回 hello
          └─ session.room 仍在且房间有该玩家
               ├─ online = true；清除宽限定时器
               ├─ 广播 room
               ├─ 发 game(mapPayload, resumed:true)
               └─ 发 resume → 客户端继续
断线 ──▶ online = false；启动 12s 定时器
          ├─ 12s 内 hello → 恢复
          └─ 超时 → forceEliminate('left') + 移出房间
```

`sessionStorage` 按标签页隔离，因此同浏览器两个标签页天然是两个玩家（FR-5.1）；清缓存/换设备即新身份，无法恢复。

### 5.9 渲染管线

```
draw(scene, now)
  ├─ 地面层：离屏 Canvas 缓存（墙/箱子/地面纹理），仅箱子变化时重建
  ├─ 道具（浮动动画）
  ├─ 炸弹（球体渐变 + 顶盖 + 引线 + 火花 + 引信环；<30% 警示）
  ├─ 爆炸（中心火球 + 四向冲击臂 + 火星，按 age/620 淡出）
  ├─ 角色（身体、方向、眼睛、被困 XX 眼与星星、队伍色环、名字）
  ├─ 本地定位箭头（画布缩小时替代名字）
  └─ HUD 由 DOM 渲染，按签名缓存，状态不变不重建
```

`viewScale = cssWidth / 660`，小于 0.58 时不再绘制角色名字，交给 HUD（FR-7.6）。

## 6. 接口与协议

### 6.1 WebSocket 消息总表

所有消息为 JSON 对象，`t` 为类型。未知类型与解析失败一律忽略（FR-5.10）。

**客户端 → 服务端**

| `t` | 载荷 | 触发 | 服务端处理 |
| --- | --- | --- | --- |
| `hello` | `{id, name}` | 连接建立/重连 | 绑定会话、接管旧连接、尝试恢复房间 |
| `create` | `{mode,bots,difficulty,teamMode,name}` | 创建房间 | 归一化配置、离开旧房、建房 |
| `quick` | 同上 | 快速匹配 | `pve` 直接开局；其余按四元组匹配或新建 |
| `join` | `{code, name}` | 输入房号加入 | 校验存在/未开局/席位；`normalizeCode()` 白名单（v1.1） |
| `ready` | `{value}` | 准备按钮 | 更新准备状态并广播（值未变化时短路，v1.1） |
| `start` | `{}` | 房主开始 | 校验房主与全部准备，调用 `Room.start()` |
| `input` | `{seq, dir?, bomb?}` | 方向变化/放弹 | `normalizeSeq()` + `isValidDir()` + `bomb === true` 校验（v1.1）；`Game.setInput()`，返回 `lastSeq` |
| `chat` | `{text}` | 房间等待期聊天（v1.1） | `normalizeChat()`（40 码点）+ 令牌桶（4 条 / 0.75 每秒），广播给房间 |
| `leave` | `{}` | 离开房间 | 对局中判负、移出、销毁空房 |
| `ping` | `{c}` | 每 3 秒 | 原样回 `pong` |

**服务端 → 客户端**

| `t` | 载荷 | 时机 | 客户端处理 |
| --- | --- | --- | --- |
| `hello` | `{id,name}` | 握手成功 | 记录自身 id |
| `room` | `{room}` | 房间状态变化 | 刷新等待界面、同步 `?room=`、绑定聊天可用性（v1.1） |
| `chat` | `{id,name,color,text,at}` | 有人发言（v1.1） | `Chat.receive()` 纯文本渲染 |
| `game` | `mapPayload` + `lineup`（开局）；重连时 `mapPayload` + `resumed:true` | 开局/重连 | 初始化地图、玩家、队伍、倒计时；禁用并清空聊天（v1.1） |
| `state` | 快照（见 6.2） | 16.7Hz 或事件 | 校正、插值、更新炸弹/爆炸/道具/HUD |
| `resume` | `{}` | 重连恢复 | 关闭断线提示，继续对局 |
| `over` | `{winner,winnerTeam,teamMode,teamNames,results,startedAt,durationMs,mode,humans,bots}` | 结算 | 渲染结算页；写入本地战绩（v1.1，`matchFromOver` + 去重键） |
| `err` | `{msg, code?}` | 非法操作 | toast 提示；`code` 含 `BAD_CODE` / `NO_ROOM` / `ROOM_LIMIT` / `NO_CODE`（v1.1） |
| `notice` | `{msg}` | 玩家离开/掉线 | toast 提示 |
| `left` | `{}` | 主动离开成功 | 回首页、清理 `?room=` 与聊天（v1.1） |
| `pong` | `{c}` | 心跳响应 | 计算 RTT（EMA 0.7/0.3） |

### 6.2 快照结构

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `players[]` | array | `{id,name,color,team,isBot,x,y,dir,moving,alive,trapped,trappedLeft,power,capacity,speed,kills,online,guard,seq}` |
| `bombs[]` | array | `{id,x,y,power,owner,left}`，`left` 为剩余引信毫秒 |
| `explosions[]` | array | `{cells:[{x,y,dir}], age}`，客户端按 `age/620` 淡出 |
| `items[]` | array | `{x,y,type}`，`type` 1=炸弹 2=火力 3=速度 |
| `changes[]` | array | `[x,y,item]`，本帧地图变化（箱子被炸） |
| `events[]` | array | `place/boom/box/pick/trap/die/save/gameover`，驱动音效与提示 |
| `timeLeft` | number | 剩余毫秒（0..180000） |
| `ended/winner/winnerTeam/teamMode` | — | 结算信息 |

`mapPayload()` 仅在开局/重连下发：`{cols,rows,seed,map[],items[],players[],teamMode,startIn,startAt}`。

### 6.4 错误与提示文案

| 场景 | 文案 |
| --- | --- |
| 房间不存在 | 房间不存在或已关闭 |

### 6.5 协议演进策略

- 新增消息只加 `t` 分支，旧客户端收到未知类型会忽略，具备前向兼容（v1.1 的 `chat` 即按此方式落地）。
- 快照新增字段是加法，客户端按需读取，不破坏旧逻辑（`over` 的 `startedAt/durationMs` 等即加法扩展）。
- 若改为二进制协议，`snapshot()` 与 `mapPayload()` 是唯一需要替换的序列化出口。

### 7.3 增量与编码

- 地图用 `Uint8Array` 存储，`mapPayload` 转普通数组；之后只发 `changes:[[x,y,item]]`，客户端把该格置空并按 `item` 记录掉落。
- 炸弹只发 `left`（剩余引信），客户端据此画进度环，不需要本地倒计时校准。
- 爆炸只发 `cells` + `age`，客户端按 `age` 计算淡出，避免每帧同步透明度。
- 道具 `type` 用整数编码（1/2/3），省字段名。

| 资源 | 创建 | 清理 |
| --- | --- | --- |
| 房间模拟定时器 | `Room.start()` | 对局结束、`Room.destroy()` |
| 自动开局定时器 | `scheduleAutoStart()` | 手动开局、触发、销毁 |
| 断线宽限定时器 | `ws.on('close')` | 重连、移出、销毁 |
| 心跳定时器 | 进程启动 | 进程退出 |
| 会话清扫器（v1.1） | 进程启动（60s 周期，`.unref()`） | 进程退出 |
| 炸弹/爆炸 | 放弹/引爆 | `tick()` 中过滤 |
| 客户端样本 | 收到快照 | 超过 12 个 shift；跳变 >3 格重置 |
| 聊天 DOM（v1.1） | 收到 `chat` | 超过 50 条移除首条；离开/开局全清 |

### 7.5 localStorage Schema（v1.1）

键名与结构由 `public/js/store.js` 定义，读取端总是先过 `normalize*` 白名单：

```
bubble.settings = {
  v: 1,                // schema 版本；读到 v > 1 时锁为只读（用默认值，永不回写）
  sfx: boolean,        // 音效总开关
```

降级路径：JSON 损坏 → 视为空；`setItem` 抛错 → 内存态（`available=false`）；

### 8.1 性能预算（设计目标）

| 项目 | 预算 | 说明 |
| --- | --- | --- |
| 单 tick 模拟 | < 5ms | 4 人 + 少量炸弹；超出会挤压广播 |

## 10. 关键架构决策（ADR）

| 编号 | 决策 | 背景 | 取舍 |
| --- | --- | --- | --- |
| ADR-1 | 服务端权威 + 客户端预测 | 纯权威手感差，纯客户端易作弊 | 增加校正复杂度，换取公平与跟手 |
| ADR-2 | 固定 50Hz 模拟、16.7Hz 广播 | 模拟稳定性与带宽的平衡 | 广播间隔内靠插值补齐 |
| ADR-3 | 移动以"精确到达时刻"续接下一格 | 每帧重置起点会丢余量，帧率相关抖动 | 实现略复杂，换来帧率无关的匀速 |
| ADR-4 | 远端 90ms 延迟 + 线性插值 | 指数平滑会"跳一下再收敛" | 远端晚 90ms，换取连续运动 |
| ADR-5 | 命中→泡封而非淘汰 | 保留"困住—补刀/救援"的核心博弈，降低暴力感 | 需要额外的被困计时与救援规则 |
| ADR-6 | AI 共用输入通道、无特权 | 避免 AI 与真人两套规则 | AI 决策必须自己算得足够好，不能靠数值补偿 |
| ADR-7 | 布局运行时求解，而非 vh 魔法数 | 移动端 vh 不稳定、HUD 换行会变高 | 需要 JS 参与布局，禁用 JS 时退回 CSS 兜底 |
| ADR-8 | 零构建、仅 1 个运行时依赖 | 降低部署与维护成本 | 无打包优化，模块靠全局对象协作 |
| ADR-9 | 内存态、无数据库 | 轻量休闲定位、零运维 | 重启丢局，扩容需外置状态 |
| ADR-10 | 乐观放弹 + 800ms 幽灵清理 | 等服务端确认会有明显延迟 | 极端情况下出现短暂幽灵炸弹 |
| ADR-11（v1.1） | 校验做成独立纯函数模块 `validate.js`，消息入口逐条调用 | 恶意/畸形输入曾直接打到业务分支；规则层不能掺网络防御 | 入口多一层函数调用；换来可单测、可复用（未来 HTTP 接口直接 require） |
| ADR-12（v1.1） | 限流用惰性令牌桶而非定时器 | 每连接挂定时器在断线风暴下开销大且难清理 | 精度到"下一次 take 时结算"，对聊天/洪水防护足够 |
| ADR-13（v1.1） | 聊天只做房间等待期的轻消息，不进对局 | 对局中聊天分散注意、也占广播带宽 | 快捷语 + 40 码点 + 双层限流；协议仍是 JSON 文本，为将来表情/信号留 `text` 字段 |
| ADR-14（v1.1） | 设置与战绩存 localStorage，UMD 同构模块 | 无数据库约束下要"刷新不丢"只能靠浏览器；且必须可单测 | schema 版本锁（未来版本只读不回写）；隐私模式降级内存态 |
| ADR-15（v1.1） | 模态弹层独立于界面状态机（不进 `el.screens`），配焦点陷阱 + inert | 设置/战绩与三屏生命周期不同：房间周期广播不应关掉正在看的弹层 | 多一套焦点管理代码；换来弹层与界面状态解耦、键盘/读屏不穿透 |

## 11. 风险与技术债

| --- | --- |
