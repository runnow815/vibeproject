## 1. 三十秒速览

一个 Q 版泡泡堂风格的联机炸弹对战小游戏。**服务端权威**：所有规则判定在服务端跑，客户端只做预测和插值。

- 服务端 50Hz 定步长模拟（`TICK_MS = 20`），每 3 个 tick 广播一次快照 → 约 16.7Hz。
- 客户端 rAF 渲染；本地用 `seq` 预测 + 服务端回 `lastSeq` 做和解；远端玩家延迟 90ms 回放 + 线性插值。
- 三种模式：玩家对战 / 人机对战 / 混合对战；支持 2v2 队伍。
- 无账号、无数据库、无构建步骤；房间状态全在内存里。

**一句话定位**：能在一台机器上跑起来的轻量休闲联机对战，规模上限是"朋友之间开几局"，不是商业服。

## 2. 环境、启动与验证

### 2.1 前置条件

| 项 | 要求 | 说明 |
| --- | --- | --- |
| Node.js | ≥ 18（`package.json` `engines`） | 只用到标准库 + `ws` |
| 依赖 | `npm install` | 运行时 `ws`，开发时 `playwright-core` |
| 浏览器（仅测试需要） | 本机 Edge，路径硬编码在测试里 | 见 2.4 的"坑位" |

### 2.2 启动

```bash
npm install
npm start          # 等价 node server/index.js，默认 http://0.0.0.0:3000
```

打开 `http://127.0.0.1:3000`。同一台机器开两个标签页即可两人对战（`sessionStorage` 按标签页隔离，天然算两个玩家）。

### 2.3 环境变量

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `PORT` | `3000` | HTTP + WS 监听端口 |
| `HOST` | `0.0.0.0` | 监听地址（局域网联机需要保持 `0.0.0.0`） |
| `MAX_ROOMS` | `500` | 房间数上限，超了 `createRoom` 返回 `ROOM_LIMIT` 错误 |

### 2.4 启动后自检

```bash
curl http://127.0.0.1:3000/health
# → {"ok":true,"rooms":0,"sessions":0,"uptime":3}
```

> **坑位**：所有浏览器测试（`test/smooth.js`、`canvas.js`、`responsive.js`、`enhance.js`）都把地址**硬编码**成 `http://127.0.0.1:3000`，并且把 Edge 路径硬编码成
> `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`。
> 跑 `npm run test:browser` **前必须先手动起服务**（`npm start` 后台挂着），测试自己不会拉服务。
> 换机器/换浏览器时需要改这 4 个文件顶部的 `EDGE` 常量。

### 3.3 脚本加载顺序（`index.html` 末尾，**不能随意调换**）

```
store → net → motion → layout → render → chat → share → panels → main
```

`main.js` 依赖前面全部；`store` 必须最先因为它们要读设置。
代码里到处是 `if (window.Xxx)` 的软依赖守卫，缺少模块时**降级而不是报错**——这是有意的，单文件缺失不会白屏。

### 3.4 两处必须知道的隐式约定

1. **输入守卫**：游戏键盘/触屏处理器里都有 `if (window.Panels && Panels.isOpen()) return;`。
   新增任何输入入口（新按钮、新快捷键、新手势）都要加这条，否则模态层打开时输入会穿透到棋盘。
2. **玩家列表重建**：`#playerList` 是整块 `innerHTML` 重建。聊天面板挂在**独立容器**里，只在房间号变化时清空——不要把聊天塞进列表里。

## 5. 协议速查（WS，JSON）

### 5.1 客户端 → 服务端

| `t` | 载荷 | 服务端校验 |
| --- | --- | --- |
| `hello` | `{id?, name}` | `normalizeId` + `sanitizeName`（12 码点、去控制字符） |
| `create` | 房间配置 | 经 `lineup.normalizeConfig` 白名单；房间数达上限 → `ROOM_LIMIT` |
| `quick` | 配置 | 同上，进入匹配队列 |
| `join` | `{code, name}` | `CODE_RE = /^[A-HJ-NP-Z2-9]{4}$/`；不存在 → `NO_ROOM` |
| `ready` | `{value}` | 值未变则短路 |
| `start` | `{}` | 房主 + 全员准备 |
| `input` | `{seq, dir?, bomb?}` | `normalizeSeq` + `isValidDir` + `bomb === true`，**任一非法整条丢弃** |
| `chat` | `{text}` | 仅 `waiting` 状态；`normalizeChat`（40 码点）+ 令牌桶 |
| `leave` | `{}` | 对局中判负 |
| `ping` | `{c}` | 原样回 `pong` |

### 5.2 服务端 → 客户端

| `t` | 时机 | 客户端处理 |
| --- | --- | --- |
| `hello` | 握手成功 | 记录自身 id |
| `room` | 房间状态变化 | 刷新等待界面；同步地址栏 `?room=` |
| `chat` | 有人发言 | 只用 `textContent` 渲染（防 XSS） |
| `game` | 开局 / 重连（`resumed:true`） | 初始化地图、队伍、倒计时 |
| `state` | 16.7Hz 或事件 | 校正、插值、更新 HUD |
| `resume` | 重连恢复 | 关断线提示 |
| `over` | 结算 | 渲染结算页 + 写本地战绩 |
| `err` / `notice` | 非法操作 / 玩家变动 | toast |
| `left` | 主动离开 | 回首页，清 URL，重置聊天 |
| `pong` | 心跳响应 | RTT（EMA 0.7/0.3） |

### 5.3 协议演进规则（**重要**）

- **加消息**：只加新的 `t` 分支，旧客户端忽略未知类型 → 天然前向兼容。
- **加字段**：快照字段只能做**加法**，客户端按需读取。改名/删字段会破坏旧客户端，禁止。
- 想换二进制协议，只需要替换 `game.snapshot()` 和 `game.mapPayload()` 两个序列化出口。

### 5.4 HTTP

| 方法 | 路径 | 响应 |
| --- | --- | --- |
| GET | `/` | `index.html` |
| GET | `/style.css`、`/js/*.js` | 对应 MIME，`Cache-Control: no-cache` |
| GET | `/health` | `{ok, rooms, sessions, uptime}` |
| GET | 越出 `public/` | 403 `forbidden`（`path.relative` + `isAbsolute` 双重判定） |
| GET | 不存在 | 404 `text/plain` |

## 6. 状态与存储

### 6.1 服务端内存态（进程重启即丢失）

| 容器 | 内容 | 清理 |
| --- | --- | --- |
| `rooms` | `Map<code, Room>`，含模拟定时器、玩家表、配置 | 无人时 `destroy()` 并清所有定时器 |
| `clients` | `Map<ws, session>` | 连接关闭时删除 |
| `sessions` | `Map<id, {..., bucket, chatBucket}>` | 60s 清扫器（`sessionSweep`）回收无房间/无玩家残留 |
| 心跳 | 30s 间隔 | 清理僵死连接 |

### 6.2 客户端持久化（localStorage）

| Key | 内容 | 备注 |
| --- | --- | --- |
| `bubble.settings` | `{v:1, sfx, volume, motion, tips}` | 音效开关 / 音量 / 减少动效 / 操作提示 |
| `bubble.stats` | `{v:1, matches:[...]}` | 最近 20 局，含胜负、淘汰数、模式、时长 |

**边界处理已经做掉的**（不要重复实现）：

- 未来版本（`v > 1`）读到时**只读默认值且绝不回写**，避免旧版本覆盖新数据。
- 写入失败（`QuotaExceededError`、隐私模式）自动降级为内存存储并置 `available = false`，功能继续可用。
- 战绩按 `id` 去重，上限 20 条，超出丢弃最旧。
- 导出 JSON 只含本机战绩，**不含任何可识别他人的信息**。

## 8. 常见维护任务 SOP

### 8.1 加一条新的协议消息

1. 服务端 `index.js` 的消息处理函数里加 `if (msg.t === 'xxx') { ... return; }` 分支。
2. 需要校验 → 在 `validate.js` 加纯函数 + 在 `validate.test.js` 加断言。
3. 需要限流 → `createBucket({capacity, refillPerSec})`，挂在 session 上。
4. 客户端 `main.js` 加 `Net.on('xxx', handler)`；广播类字段只增不改。
5. `test/chat.test.js` 之类加一条端到端断言。

### 8.2 加一个设置项

1. `store.js`：`DEFAULTS` 加字段 + `normalizeSettings` 加白名单校验。
2. `panels.js`：在设置面板加控件，走 `on('change')` → 保存（有防抖）。
3. `main.js` 的 `applyPrefs(prefs)` 里应用。
4. 升级存什么：**不要**改 `v`，`v` 只在 Schema 破坏性变更时递增。

### 8.3 改游戏规则

只改 `game.js`，然后：
- 跑 `game.test.js` + `team.test.js`；
- 若影响胜负判定，`net.test.js` 的双端一致性断言会兜底；
- **不要**为了规则去改 `index.js` 的广播逻辑——规则变动应通过快照字段体现。

### 8.4 调 AI

改 `bot.js` 的 `PRESET` 或决策函数。注意：
- `bot.js` **只能**通过 `game.setInput()` 改变世界，读地图只能用 `blastPreview()` 等只读方法——这条是硬约束（FR-4.1），破坏它等于让 AI 绕过权威判定。
- `bot.test.js` 是真实计时的（约 6 秒），改"会行动/会逃生/会挣扎"任一条行为都会让它挂。

### 8.5 调同步手感

- 卡顿/抖动 → 看 `REMOTE_DELAY`（90ms）和远端样本数（12，跳变 >3 格重置）。
- 本地拉扯感 → 看硬校正阈值（2.4 格）和衰减速度。
- 一格耗时 → `motion.js` 的 `{base:150, step:0.82, min:78}`，改完必须过 `motion.test.js` 的帧率无关断言。

### 8.6 改 UI / 样式

- 新增弹层：复用 `Panels` 的模态机制（焦点陷阱 + Esc + 背景 `inert`），不要自己造。
- 新增输入入口：加 `Panels.isOpen()` 守卫（见 3.4）。
- 改布局后跑 `responsive.js`——它会断言无横向溢出、棋盘恒为 15:13、正文 ≥12px、触控目标 ≥44px。

| --- | --- |
| 新增道具 | `game.js` 的道具表 + `render.js` 画法；数据结构已预留 `power` / `owner` |
| 新增模式 | `lineup.js` 的 `VALID_LINEUPS` + `main.js` 的模式切换 |
| 新增客户端模块 | 新建 `public/js/*.js`，挂 `window.Xxx`，在 `index.html` 按依赖顺序插入 |
| 新增服务端校验 | `validate.js` 加纯函数 |
| 观战 / 回放 | 快照本身就是可序列化帧序列，直接落盘即可 |
| AI 协同策略 | `bot.js` 内加"跟随队友 / 让路 / 集火"，不影响外部接口 |

### 9.2 别碰 / 碰了要连带改一堆

| 事项 | 为什么 |
| --- | --- |
| 快照字段改名或删除 | 破坏旧客户端；协议只承诺加法 |
| `normalizeConfig` 的白名单 | 它是安全边界，加字段必须同步 |
| `bot.js` 绕过 `setInput` | 等于绕过服务端权威 |
| `layout.js` 的 15:13 求解 | 响应式测试的全部断言都建立在它上面 |
| 模态层的 `inert` / 焦点陷阱 | 拿掉会让键盘输入穿透到棋盘 |
| 聊天用 `innerHTML` 渲染 | 现网唯一的用户可控文本入口，必须 `textContent` |

### 9.3 明确**未做**、且做之前要先想清楚的事

- **观众席**：`Room.broadcast` 只遍历 `players`，`normalizeConfig` 又是白名单，加观众需要**非对称**改动（广播加收件人集合）。v1.1 有意排除。
- **横向扩容**：房间在内存里，多进程需要按房间号做一致性哈希 + 外置状态。
- **账号体系**：当前 id 在 `sessionStorage`，可伪造，但**只能影响自己的席位**，无资产风险。要加账号就要连带改握手、房间归属、战绩归属。

## 10. 已知限制与技术债务

| 编号 | 债务 | 影响 | 建议处理 |
| --- | --- | --- | --- |
| T-1 | 单进程内存态，重启丢局 | 中 | 休闲定位可接受；要扩容先外置房间状态 |
| T-2 | 纯 JSON 广播，带宽随房间/人数线性增长 | 中 | 4 人局无压力；量大再换二进制或按 AOI 裁剪 |
| T-3 | ~~无输入频率限制~~ **v1.1 已修**（令牌桶 + 洪水断开） | — | 已闭环 |
| T-4 | 无账号与持久化战绩（仅本机 localStorage） | 低 | 加账号前先定归属模型 |
| T-5 | 浏览器测试硬编码 Edge 路径与 3000 端口 | 低 | 换环境时改 4 个文件顶部常量 |
| T-6 | `CODE_RE` 在 `server/validate.js` 与 `public/js/share.js` 各存一份 | 低 | 前端无法 `require`，靠注释同步；改动时**两处都要改** |
| T-7 | 房间号空间约 32⁴ ≈ 104 万 | 低 | 小规模够用；**不作为安全边界** |
| T-8 | iOS 音频需首次交互后才能播放 | 低 | 浏览器策略，无音效也能完整游玩 |
