## 1. 项目概述

### 1.1 背景

《Q版泡泡堂》一类游戏的核心乐趣是"走位—放炸弹—炸开箱子—捡道具—把对手困住—补刀或救援"的短周期博弈。原作以客户端单机/房间制为主，本项目要在一个**无需安装、打开网页就能玩**的载体上复刻这套循环，并补上**实时联机**与**人机/混合对局**，让"一个人也能玩、两个人就能开、四个人最热闹"。

### 1.2 产品目标

| 编号 | 目标 | 可验证的成功标准 |
| --- | --- | --- |
| G1 | 还原核心玩法循环 | 移动、放炸弹、十字冲击、炸箱掉道具、泡封、补刀/救援、胜负结算全部可用 |
| G2 | 2–4 人实时联机 | 两台客户端收到同一份权威状态；远端移动连续无跳变；断线 12 秒内可恢复 |
| G3 | 单人可玩、混合可玩 | 1 真人 + 1–3 AI 可立即开局；混合局支持 1–4 真人 + 1–4 AI 且总数 ≤ 4 |
| G4 | 多端可用 | 320×568 至 1920×1080 共 9 个典型视口下棋盘完整、无横向溢出、可正常操作 |
| G5 | 低门槛交付 | 零构建、零图片资源、仅 1 个运行时依赖（`ws`），`npm start` 即可运行 |

### 1.3 范围

**本期包含**

- 三种对局模式：玩家对战（`pvp`）、人机对战（`pve`）、混合对战（`hybrid`）。
- 4 位房间号建房/加入、快速匹配、2v2 分队、等待与准备、结算与回到房间。
- 完整对局规则：地图生成、移动、炸弹、连锁爆炸、箱子与三种道具、泡封/挣扎/补刀/救援、出生保护、计时与胜负。
- 服务端 AI：三档难度，与真人共用输入通道与判定规则。
- 联机同步：服务端权威、客户端预测、远端插值、状态增量、断线重连、心跳。
- 响应式布局、触控操作、键盘操作、基础无障碍。
- 自动化测试：逻辑单测、联机端到端、AI 行为、浏览器移动平滑度、Canvas 视觉、9 视口响应式。

**本期不包含**

- 账号体系、好友、排行榜、战绩持久化（无数据库）。
- 大厅列表、跨房间聊天、观战与回放。
- 踢炸弹、投掷炸弹、遥控炸弹、坐骑等扩展道具。
- 多进程/多机部署与房间迁移（当前为单进程内存态）。
- 付费、广告、社交分享。
- 公网 NAT 穿透/中继（需自行部署到可访问的主机）。

### 1.4 术语表

| 术语 | 含义 |
| --- | --- |
| 格（cell） | 地图的整数坐标单位，15 列 × 13 行；碰撞与所有规则判定都以格为准 |
| 连续坐标（px/py） | 角色在格与格之间的浮点位置，仅用于广播与渲染 |
| 泡封（trapped） | 被冲击命中后的"眩晕/被困"状态，不立即出局，计时结束才淘汰 |
| 补刀 / 救援 | 对手踩到被困者所在格 → 淘汰；分队模式下队友踩到 → 解除被困并给短暂无敌 |
| 权威快照 | 服务端按固定节奏广播的完整对局状态，是客户端唯一的真相来源 |
| 预测 / 校正 | 客户端在本地先按同一套规则移动，收到快照后按策略对齐 |
| 插值 | 远端玩家按"延迟 90ms + 样本间线性插值"回放，消除快照频率带来的顿挫 |
| 席位 | 一个房间内的参战位置，真人席位 + AI 席位总数 ≤ 4 |
| RTT | 往返时延，客户端每 3 秒探测一次并在顶栏展示 |

## 2. 目标用户与核心使用场景

### 2.1 目标用户

| 编号 | 用户类型 | 特征 | 核心诉求 | 对应设计 |
| --- | --- | --- | --- | --- |
| U1 | 怀旧休闲玩家 | 玩过泡泡堂/QQ 堂，熟悉"放泡泡困人"的规则 | 打开就能玩，规则别走样 | 还原泡封、补刀、炸箱掉道具；道具图鉴可查 |
| U2 | 朋友小聚（2–4 人） | 同一局域网或语音里约战，愿意发房间号 | 建房简单、开局快、状态同步准 | 4 位房间号、准备/开始、服务端权威 |
| U3 | 单人练习/等人 | 只有自己，不想空等 | 立刻有对手，难度可调 | 人机对战一键开局；三档难度 |
| U4 | 混合局组织者 | 真人不齐，想用 AI 补位 | 人数规则清晰、队伍平衡 | 混合模式 6 种合法组合；AI 补人少一队 |
| U5 | 移动端/平板玩家 | 触屏、竖屏或横屏、网络一般 | 能看清、能按准、横屏不憋屈 | 响应式布局、44px 触控目标、横屏摇杆分列两侧 |

### 2.2 核心使用场景

| 编号 | 场景 | 前置条件 | 主流程 | 成功标准 | 关联需求 |
| --- | --- | --- | --- | --- | --- |
| SC-1 | 两位朋友开房对战 | 双方能访问同一服务地址 | A 创建房间 → 把 4 位房号发给 B → B 加入 → 双方准备 → 房主开始 → 对局 → 结算 | 两端进入同一局，地图与出生点一致，能互相炸中 | FR-2.1、FR-2.5、FR-2.6、FR-3.*、FR-5.* |
| SC-2 | 四人快速匹配混战 | 4 人在相近时间点击快速匹配 | 各自选"玩家对战"→ 快速匹配 → 并入同一等待房或新建 → 人满/房主开始 | 4 人同房，座位与颜色不重复 | FR-2.2、FR-2.6 |
| SC-3 | 单人打 AI | 无 | 首页选"人机对战"→ 选难度与 AI 数量 → 快速匹配 | 立即开局，AI 会移动、放炸弹、逃生、挣扎 | FR-1.3、FR-2.3、FR-4.* |
| SC-4 | 混合局补位 | 1–3 名真人 | 选"混合对战"→ 设 AI 数量（决定真人席位）→ 建房/匹配 → 真人到齐或 12 秒自动开局 | 真人与 AI 同场，总数 ≤ 4，席位提示准确 | FR-1.2、FR-2.4、FR-2.8 |
| SC-5 | 2v2 分队 | 总人数正好 4 | 建房时勾选"2v2 分队"→ 开局 | 两队人数差 ≤ 1；队友免伤；队友踩中为救援；按队伍判胜负 | FR-1.6、FR-3.7、FR-3.9、FR-3.11 |
| SC-6 | 手机横屏对局 | 触屏设备、横屏 | 打开页面 → 触摸后出现摇杆 → 对局 | 棋盘完整可见；摇杆在左右两侧；点按不误触滚动 | FR-8.5、FR-8.6、FR-9.1 |
| SC-7 | 对局中短暂断网 | 对局进行中 | 网络抖动/切后台 → 自动重连 → 恢复对局 | 12 秒内回到原局，地图与当前状态完整 | FR-5.7、NFR-3 |
| SC-8 | 对局结束后再来一局 | 结算页 | 点"回到房间"→ 重新准备 → 房主开始 | 房间配置保留，玩家仍在房内 | FR-6.5、FR-2.6 |

### 2.3 用户旅程

```
首页（名字 / 模式 / 难度 / AI 数量 / 分队）
   │  快速匹配            创建房间            加入房间
   ▼                       ▼                   ▼
匹配成功 / 建房 ────────▶ 房间（房号、真人+AI 列表、准备、开始、自动开局倒计时）
   │                                              │
   │ 人机对战：直接开局                            │ 房主开始（其他在线玩家已准备）
   ▼                                              ▼
对局（2.2s 倒计时 → 1.6s 出生保护 → 3 分钟对局 → HUD / 摇杆 / 音效）
   │
   ▼
结算（名次、胜者/胜队、淘汰数、AI 标记）──▶ 回到房间 ──▶ 再来一局
```

### 2.4 关键体验指标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 按键到本地起步 | ≤ 1 帧（实测 ≤ 14ms） | 在 `keydown` 内直接起步，不等下一帧 |
| 单格移动耗时 | 恒定 150ms（速度 0 级） | 与显示器刷新率无关（30/60/120/144Hz 一致） |
| 远端位置延迟 | 约 90ms | 插值回放的固定代价，换取连续运动 |
| 校正收敛 | 约 150ms 内衰减到 10% 以内 | 偏移指数衰减，避免橡皮筋 |
| 断线恢复窗口 | 12 秒 | 超时判负并移出房间 |
| 对局时长 | 180 秒 | 超时按淘汰数/队伍淘汰数排名 |

## 3. 功能需求

优先级定义：**P0** 缺失即不可发布；**P1** 影响体验但可短期缺失；**P2** 增强项。

### 3.1 FR-1 对局模式与阵容配置

| 编号 | 需求 | 规则 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-1.1 | 提供三种对局模式 | `pvp` 玩家对战、`pve` 人机对战、`hybrid` 混合对战；首页可切换，非法值回退 `pvp` | P0 |
| FR-1.2 | 人数硬约束 | `1 ≤ 真人 ≤ 4`、`1 ≤ AI ≤ 4`、`真人 + AI ≤ 4`；混合模式合法组合固定为 6 种（见 4.3） | P0 |
| FR-1.3 | 配置归一化 | `pvp` 强制 `bots = 0`；`pve`/`hybrid` 的 `bots` 收敛到 1–3；`difficulty` 仅接受 1/2/3，默认 2 | P0 |
| FR-1.4 | 真人席位计算 | `pvp → 4`、`pve → 1`、`hybrid → 4 − bots`；建房时按 AI 数量确定真人席位并在界面展示 | P0 |
| FR-1.5 | 非法阵容拒绝 | 任何越界组合返回可读原因（如"真人 + AI 总数不能超过 4 人（当前 3 + 2）"），不进入对局 | P0 |
| FR-1.6 | 2v2 分队 | 仅在总人数 = 4 且勾选分队时生效；不满足时自动降级为混战，并在界面说明 | P1 |
| FR-1.7 | 模式说明可见 | 首页展示当前模式的人数含义（AI 数量 → 真人席位）、难度、分队开关；人机/混合模式才显示 AI 配置 | P2 |

### 3.2 FR-2 房间与匹配

| 编号 | 需求 | 规则 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-2.1 | 创建房间 | 生成 4 位房间号，字符集为 32 个易辨识字符（去掉 `I/O/0/1`）；冲突最多重试 50 次 | P0 |
| FR-2.2 | 快速匹配 | 以 `(mode, bots, difficulty, teamMode)` 四元组为键，优先并入"等待中且仍有真人席位"的房间，否则新建 | P0 |
| FR-2.3 | 人机对战直接开局 | `pve` 不走匹配，创建房间后立即开局（1 真人 + 配置的 AI） | P0 |
| FR-2.4 | 混合房自动开局 | 快速匹配新建的混合房带 12 秒倒计时；到点按"当前真人 + 配置 AI"开局，中途加入者一并参战 | P1 |
| FR-2.5 | 加入校验 | 房间不存在 / 对局已开始 / 真人席位已满，分别给出明确提示；席位满时说明"已配置 N 个 AI" | P0 |
| FR-2.6 | 准备与开始 | 只有房主可点开始；除房主外的在线玩家必须全部准备；非房主点开始返回错误提示 | P0 |
| FR-2.7 | 离开房间 | 等待中离开直接移出；对局中主动离开判负并广播提示；房间无真人时销毁并清理定时器 | P0 |
| FR-2.8 | 等待界面信息完整 | 展示房号、模式、难度、分队、真人列表（含房主标记/在线状态）、AI 占位列表、真人席位数、自动开局倒计时 | P0 |
| FR-2.9 | 回到房间 | 结算后房间状态回到等待，玩家保留，准备状态清空，可用原配置再来一局 | P1 |

### 3.3 FR-3 对局核心玩法

| 编号 | 需求 | 规则 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-3.1 | 地图生成 | 15×13；外圈为不可破坏墙；`x`、`y` 均为偶数的内部格为墙；其余格 72% 概率为箱子；四个出生点及其上下左右清空（只清内圈）；中心 3×3 清空 | P0 |
| FR-3.2 | 移动 | 键盘 `WASD`/方向键、触屏方向键；按格移动，单格耗时 `max(78, 150 × 0.82^speed)` ms；墙、箱子、任意炸弹所在格不可进入；松键走完当前格即停 | P0 |
| FR-3.3 | 放炸弹 | `空格`/`J`/`K`、触屏按钮；受 `capacity` 限制；同格不可重复放置；移动中取"更近的一格"；倒计时/被困/出局时不可放 | P0 |
| FR-3.4 | 爆炸与连锁 | 引信 2400ms；以炸弹为中心向四方向推进 `power` 格；遇墙停止；遇箱子炸开并停止；遇其他炸弹立即连锁引爆；命中在引爆瞬间判定，爆炸视觉残留 620ms | P0 |
| FR-3.5 | 箱子与道具 | 箱子被炸开有 36% 概率掉落道具；掉落类型中炸弹 +1 占 40%、火力 +1 占 38%、速度 +1 占 22%；踩到即拾取并立即生效 | P0 |
| FR-3.6 | 属性上限 | 火力 ≤ 7、同时炸弹数 ≤ 6、速度等级 ≤ 3 | P0 |
| FR-3.7 | 泡封而非直接淘汰 | 被冲击命中进入被困状态，持续 4200ms，期间不能移动/放炸弹；计时结束自行出局 | P0 |
| FR-3.8 | 挣扎 | 被困时反复按方向键可缩短被困时间：每次 −140ms，最短 1500ms，两次之间至少间隔 110ms | P1 |
| FR-3.9 | 补刀与救援 | 对手走入被困者所在格 → 淘汰；分队模式下队友走入 → 解除被困并获得 900ms 无敌 | P0 |
| FR-3.10 | 队伍免伤 | 分队模式下，队友的炸弹冲击不造成被困 | P0 |
| FR-3.11 | 开局保护 | 开局 2200ms 倒计时内不可操作；倒计时结束后 1600ms 出生保护，期间不被冲击命中 | P0 |
| FR-3.12 | 胜负判定 | 混战：最后存活者胜；180 秒到点按淘汰数（仅统计存活者）。分队：一队全灭即结束；到点按队伍总淘汰数，其次比存活人数 | P0 |
| FR-3.13 | 淘汰计数 | 造成被困者出局的一方 `kills + 1`；自我炸中导致的出局不计给他人 | P0 |
| FR-3.14 | 出生点分配 | 混战 2 人用对角、3 人取前三个角、4 人占四角；分队时同队同一侧、两队隔图相望（见 4.4） | P0 |

### 3.4 FR-4 AI 对手

| 编号 | 需求 | 规则 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-4.1 | AI 无特权 | AI 只能向 `Game.setInput()` 提交 `{dir, bomb}`，与真人共用移动、放弹、命中、胜负判定；不得穿墙、瞬移或获得额外数值 | P0 |
| FR-4.2 | 危险感知 | 每次决策构建危险图：所有活跃炸弹的爆炸范围与挨炸时刻；连锁引爆按上游引爆时刻 + 80ms 传播 | P0 |
| FR-4.3 | 逃生 | 站在危险格时用带时间预算的 BFS 寻找"爆炸结束后仍安全"的落脚点，优先非死胡同；无解时选最优劣解 | P0 |
| FR-4.4 | 放弹决策 | 安全时评估放弹收益（能命中对手/能炸开箱子/不伤队友），并先在虚拟地图上验证"放完能逃掉"才落子 | P1 |
| FR-4.5 | 目标选择 | 无威胁时按"最近道具 → 最近对手 → 最近可炸箱位置"行动；到达新格立即重规划 | P1 |
| FR-4.6 | 难度分层 | 三档只调整思考间隔、抖动、失误率、搜索深度、追击权重，不修改任何数值上限 | P0 |
| FR-4.7 | 被困挣扎 | AI 被困时同样会挣扎，而非原地等待出局 | P1 |
| FR-4.8 | 生命周期独立 | AI 不占用 WebSocket 连接；真人掉线/离开后 AI 仍可打完整局 | P1 |

### 3.5 FR-5 联机与同步

| 编号 | 需求 | 规则 / 验收标准 | 优先级 |
| --- | --- | --- | --- |
| FR-5.1 | 连接与身份 | 通过 WebSocket 连接；`sessionStorage` 保存客户端 id（按标签页隔离，同浏览器两个标签页 = 两个玩家）；`hello` 完成握手 | P0 |
| FR-5.2 | 输入上报 | 客户端发送 `{t:'input', seq, dir, bomb}`；服务端在快照中回传每个玩家的 `lastSeq` | P0 |
| FR-5.3 | 本地预测 | 方向键按下即本地起步；放炸弹做乐观渲染，800ms 内未被权威列表确认则移除"幽灵炸弹" | P0 |

### 4.3 混合模式合法人数组合

| 真人 | AI | 总数 |
| --- | --- | --- |
| 1 | 1 | 2 |
| 1 | 2 | 3 |
| 1 | 3 | 4 |
| 2 | 1 | 3 |
| 2 | 2 | 4 |
| 3 | 1 | 4 |

约束推导：因至少 1 名真人，`AI = 4` 在混合模式不可能出现，故配置值实际为 1–3。

### 4.4 队伍与出生点分配

1. 仅当总人数 = 4 且勾选分队时启用，否则混战。
2. **真人蛇形轮转**：按加入顺序 `0→蓝, 1→红, 2→蓝…`，保证两队真人数量差 ≤ 1。
3. **AI 补位**：每个 AI 分配给当前人数较少的一队（相等时补蓝队），保证两队总人数差 ≤ 1。
4. **出生角**：蓝队用左侧两角 `(1,1)`、`(1,11)`；红队用右侧两角 `(13,1)`、`(13,11)`；混战 2 人用对角，3–4 人依次占四角。

### 4.5 胜负判定

| 情形 | 混战 | 分队 |
| --- | --- | --- |
| 场上仅剩 1 人 / 1 队 | 该玩家胜 | 该队胜 |
| 180 秒到点 | 存活者中淘汰数最高者胜；并列取先遍历到者 | 队伍总淘汰数高者胜；相同则存活人数多者胜 |
| 全部出局 | 平局（无胜者） | 平局（无胜队） |
| 主动离开 / 宽限期超时 | 判负 | 判负 |

### 4.6 玩家状态机

```
等待开局 ──倒计时结束──▶ 存活（可移动/放弹）
                          │ 被冲击命中
                          ▼
                        被困（4.2s，可挣扎）
                     ┌────┴─────┐
             对手踩中 │          │ 计时结束 / 队友未及时救援
                     ▼          ▼
                   出局 ◀───────┘
                     ▲
        队友踩中（分队）│ 解除被困 + 900ms 无敌 → 回到存活
```

| NFR-7 | 可扩展性 | 新增道具/模式不需改动同步管线；协议以 `t` 字段扩展；房间状态可迁移到多进程（一致性哈希） | 架构审查 |
| NFR-8 | 可访问性 | 允许缩放；正文 ≥ 12px；触控目标 ≥ 44px；键盘全流程可达；尊重减少动效/高对比度偏好 | `test/responsive.js` 断言字号与触控目标 |
| NFR-9 | 可观测性 | `/health` 返回房间数与运行时长；自动开局失败等异常写 `console.warn` | 手工请求 `/health` |
| NFR-10 | 部署与成本 | 单进程、无数据库、无构建步骤；`npm install && npm start` 即可运行；静态资源与 WS 同端口 | 本地/局域网启动验证 |

### 6.2 发布门槛

1. `npm test` 全部通过（7 个文件，54 项断言）。
2. `npm run test:server` 全部通过（v1.1 校验/存储/聊天/健壮性，42 项断言）。
3. `npm run test:browser` 全部通过：移动平滑度（速度波动 ≤ 1%、停顿帧 = 0）、Canvas 视觉帧、9 视口响应式、v1.1 体验增强 45 项。
4. 手工冒烟：三种模式各开一局；双标签页互打；断网 5 秒后恢复；手机横竖屏各一局；复制邀请链接在另一台设备加入。

### 6.3 已知限制

- 无账号与持久化，服务重启会丢失进行中的对局（本地设置与战绩不受影响）。
- 房间号空间约 32⁴ ≈ 104 万，适合小规模使用；不作为安全边界。
- iOS 音频需首次用户交互后才能播放（浏览器策略）。
- 聊天仅在等待阶段可用，对局中无快捷信号（v1.2 方向）。
- `inert` 属性在极旧浏览器上不生效，焦点仍由 Tab 陷阱与 Esc 兜底。

## 8. 风险与假设

| 编号 | 类型 | 描述 | 影响 | 应对 |
| --- | --- | --- | --- | --- |
| R-1 | 技术 | 纯 JSON 广播，房间数/人数上升后带宽与序列化开销线性增长 | 中 | 当前 4 人局可接受；后续可换二进制协议或按 AOI 裁剪 |
| R-2 | 技术 | 单进程内存态，重启即丢失对局 | 中 | 定位为轻量休闲服务；扩容路径见架构文档 |
| R-3 | 安全 | ~~未限制输入消息频率~~ **已于 v1.1 缓解**：令牌桶限流 + 16KB 帧上限 + 洪水断开（FR-15） | 低 | `robust.test.js` 持续验证 |
| R-4 | 安全 | 客户端 id 存于 `sessionStorage`，可被伪造 | 低 | 仅能影响自身席位；无账号资产 |
| R-5 | 体验 | 移动端音频受浏览器自动播放策略限制 | 低 | 首次交互后解锁；无音效也可完整游玩 |
| R-6 | 隐私 | 本地战绩/设置存于 localStorage，同机其他页面不可读但可被用户清除 | 低 | 仅存本机、不含他人可识别信息；提供一键清空 |
| A-1 | 假设 | 玩家设备支持 WebSocket 与 Canvas 2D | — | 不支持时提示升级浏览器 |
| A-2 | 假设 | 单房间参战者 ≤ 4 | — | 人数上限在协议与规则层双重校验 |
| A-3 | 假设 | 部署在可被玩家直接访问的主机（局域网或公网） | — | README 说明用内网 IP 访问 |
