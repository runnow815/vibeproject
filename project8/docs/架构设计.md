# 墨战（project8）架构设计

> 配套：[需求文档](./需求文档.md) · [可视化原型](./prototype.html)
> 本文描述 v1.0 单机人机版的实现架构，并说明为未来联机预留的演进路径。

---

## 1. 技术选型

| 维度 | 选型 | 理由 |
|---|---|---|
| 形态 | 单文件 `inkwar.html`（CSS+HTML+JS 内联） | 仓库铁律：零依赖、零构建、双击即玩（见 CLAUDE.md） |
| 渲染 | Canvas 2D 全量重绘 | 实体为大量圆点/圆环，Canvas 足够且省事；不需要 DOM 动画级联 |
| 逻辑 | 原生 JS（`'use strict'` + IIFE） | 与 project1~7 一致 |
| 音效 | WebAudio 振荡器合成 | 无音频文件，`Sound.tone()` 基础合成器 + 各事件音效方法 |
| 存档 | localStorage（前缀 `ink.`） | 闯关进度/最快胜利/音效开关/上次配置 |
| 模拟 | **固定步长 1/30s + 命令驱动** | 逻辑确定性时间轴；渲染只读状态，二者解耦 |

**为什么不做 ECS / WebSocket / 定点数**：单机人机不需要跨设备确定性（浮点即可）、单位规模 ≤300（O(n) 结算足够）、无后端。Cocos/Laya、Go 后端、帧同步服务器均为原版墨战的工程语境，本期仅保留**可演进的结构**（见第 8 节）。

## 4. 模拟循环与命令系统

### 4.1 固定步长推进

```js
// UI 层主循环
loop(t) {
  acc += min(50, t - last);            // dt 钳制，防后台切回大跳帧
  while (acc >= STEP && mode === 'playing') {
    InkSim.step(sim, STEP);            // 每步固定 1/30s，一次只推一步
    acc -= STEP;
  }
  draw(); requestAnimationFrame(loop);
}
```

单步内顺序（需求文档 F2）：**命令队列 → 产兵 → 部队推进/抵达结算 → 在途遭遇（异主湮灭）→ 阵列迎敌 → 过城开战（v1.23）→ 阵列计时与空阵列清场 → 增益倒计时 → 墨量回复 → AI → 胜负判定**。命令在步首执行，保证「本帧点击、本帧生效」。

> v1.22：原「阵列散逸（每 5 秒 -1 兵）」环节已移除，仅保留 `atkT` 计时与 `count < 1` 清场；屯兵永久驻守。
>
> v1.23：新增「过城开战」——在途部队进入 `castleR(c) + armyR(pa)` 且 `c.owner !== pa.owner` 即互耗（`min(兵力, ⌊驻军⌋)`，**不占领**），跳过己方城 / 护盾城 / 当前目标城 / 空城。`castleR` 由逻辑块导出、渲染层复用（同一把尺子）。
>
> v1.24：三处插入新规则 —— ① **产兵段**：`plagueT > 0` 的城跳过产兵、改为 `- PLAGUE_RATE·dt`（R11）；② **抵达结算**：护盾分支之后、`R3` 之前先跑伏兵（R10，一次性、吃光即止）；③ **计时器段**：`tower.temp` 到期即 `tower = null`（R12）。另有 `armySpeed` 追加 `slowT → ×SLOW_MUL`（R14）。
>
> v1.24：胜负判定段末尾追加**关卡目标结算**（`sim.opts.goal`）。顺序是「先清空兜底、后目标」且 **`over` 已定则不再改写**——清空永远是最高的胜利方式，守城关不会在最后一秒把已经赢下的局判输。
>
> v1.25：**块1 只增四处，且不改变任何判定与随机序列** —— ① `loss()` 伤亡记账（纯累加，插在既有减员点上）；② `DIFF.master` 表项；③ `opts.custom` 落地（`inkStart` 改初值、`capMul/prodMul` 乘进 `sim.mods`）；④ 胜负段追加 `goal.type === 'time'` → `timeWinner()`（占城数 → 其次总兵力）。默认不传参时与 v1.24 逐字节等价，既有 315 条断言零修改全绿。

```js

InkSim.cardPlay(sim, { key: 'fire', targetId? })   // 已校验墨量；不合法返回 false

// send 内部：每座来源城 floor(garrison × ratio) 兵 → 生成 Army（出兵城 garrison 同步扣减）
// to 为 {x,y} 时：出城兵最后 1 个 Army 抵达点生成/并入 Camp（阵列）
```

这个收口是刻意设计：**模拟的因果链 = 命令流**。录下一局所有命令 + 种子即可完整回放，也是未来帧同步所需的全部输入。

### 4.3 战斗结算（F3 的实现要点）

- 抵达己方城：`garrison = min(garrison + count, cap)`；若 `garrison >= up 且 level < 3` → 调 `upgradeCastle()` 扣 `up` 升级（每步最多升 1 级，余量留到下一步）。
- **主动升级（v1.32）**：UI 只入队 `{type:'castleUp', owner, id}`；step 命令阶段由 `doCastleUp()` 校验归属/兵力/等级后调用同一个 `upgradeCastle()`。Lv1→2 扣 20，Lv2→3 扣 50，成功事件携带 `{id,owner,spent,level}`；自动升级与主动升级不会出现两套数值。
- 抵达敌/中立城：护盾生效则部队消散；否则 `count > garrison` → 易主（驻军 = 差值并**按新城池容量封顶**，等级保留，占领方墨量 +2/+1），否则 `garrison -= count`。
- 抵达阵列：同主并入，异主**不交互**（本期取舍，见第 7 节）。
- **在途遭遇（墨色相溶）**：推进后对所有 Army 做同帧两两检测，异主且距离 ≤ `CLASH_R`（16）→ 双方按 `min(countA, countB)` 互相湮灭，归零者移除（不变量 count ≥ 1 由此维持），并推送 `clash` 事件供表现层画墨晕。复杂度 O(n²) 但 n ≤ 300（ARMY_CAP），每步 ≤ 4.5 万次距离判定，性能无忧。

### 4.4 防御塔开火（v1.12）

塔是**城池的附属状态**（`Castle.tower`），不开独立实体，因此天然满足「占领后塔随城易主」的设定：

- **生成**：`mapGen` 在点位与驻军全部定完后统一掷点 `maybeTower()`（主城 0.5 / 中立 0.3）；塔种从 `TOWERS` 均匀取。
- **成长**：`resolveArrival` 的升级分支末尾调用 `maybeBuildTower()`（0.45）——无塔则建 Lv1，有塔则在 < 3 时升一级。
- **开火（v1.32 补阵列索敌）**：置于移动与抵达结算**之后**（step 3.7）。冷却就绪后分别扫描 `sim.armies`（在途部队）和 `sim.camps`（驻扎阵列），统一过滤死亡/己方/射程外目标并取距离最近者；`towerHit()` 统一扣兵与伤亡记账，炮塔 `towerSplash()` 同时波及落点附近两类敌军，爪子对两类目标都按比例抓兵。随后目标置 `atkT`、塔进入冷却并推送 `tower` 事件，最后统一过滤 `count < 1` 的部队/阵列。
  - **根因记录**：旧循环只遍历 `sim.armies`。部队抵达空地后会从 `armies` 删除并创建 `Camp`，因此塔并非冷却/射程/遮挡异常，而是目标从候选列表中永久消失——表现为“部分塔不攻击”（其实四种塔都无视阵列）。
  - 塔没有弹药、遮挡或激活开关；合法停火只可能是 `tower.cd > 0` 或射程内没有异主存活目标。
- **顺序理由**：放在抵达结算之后，塔火与「抵达即占领/消耗」不会在同一步重复作用于同一支部队。
- **随机源隔离**：塔的掷点走 `sim.trng`（`seed ^ 0x5f3759df` 派生的第二条 `mulberry32`），**不消耗主线 `rng`** —— 开/关塔不改变地图点位、中立驻军与手牌，既有 100+ 条断言无需改动。

### 4.5 攻击动作为纯表现层（v1.12）

`atkT`（部队/阵列）与 `hitT`（城池）只是**计时器**，不参与任何战斗结算：

- `armyFormations()` 为每个兵算独立攻击相位 `ap = (id·5.31 + k·2.399) % 6.283` 与个体步频 `24 + (k%5)·1.6`，输出 `atk ∈ [0,1]`；`drawArmy` 据此给每个兵各自的突刺位移与挥砍弧（**上限 24 道**）。
  > 教训：最初直接复用行军相位 `ph·2.6`，因相邻兵相位差 2.399×2.6 ≈ 2π − 0.046 产生**混叠**，全队会同步成「一个人在砍」；改用独立系数后任一时刻约四成兵在挥砍。
- 阵列兵走 `campFormations()` 的同套公式（由 `p.atkT` 驱动），驻城环兵由 `c.hitT` 驱动整环抖动——三处共用同一时间参数，观感统一。

### 4.6 牌库循环（v1.14，杀戮尖塔式）

实时局没有「回合」，因此把尖塔的「回合开始抽 5 张」映射为**定时抽牌**，其余（四堆、洗牌、消耗）原样保留：

| 环节 | 实现 | 说明 |
|---|---|---|
| 建堆 | `createGame` 里**每个参战阵营（1~4）**各建一副：`piles[owner].list = (opts.decks[owner] || DEFAULT_DECK).slice()`，`draw = shuffle(list, drng)`，随后抽 `START_HAND=3` 张 | v1.16 起 AI 阵营 2/3/4 同样有牌堆（不再绕过牌库直接施放）；AI / 联机对手一律用 `DEFAULT_DECK`（不吃玩家存档，保证公平） |
| 抽牌 | step 内 `drawAcc[owner] += dt`；`hand.length < HAND_MAX(5)` 且 `drawAcc ≥ DRAW_T(6)` → `drawAcc -= DRAW_T; drawOne()` | 手牌满时计时器**保持待抽**，不满即补——不会白白浪费一次抽牌 |
| 洗牌 | `drawOne` 发现 `draw` 空且 `discard` 非空 → `discard` 经 `drng` Fisher–Yates 洗入 `draw`，推 `{type:'shuffle', owner}` 事件 | 消耗堆**不参与**洗牌；两堆皆空则本局不再有牌可抽 |
| 出牌 | `cardPlay`：`hand.splice(slot,1)` → `card.ex ? exhaust.push(key) : discard.push(key)` | **不再「打一张补一张」**（v1.14 前的行为），牌的稀缺性由此产生 |
| 升级版 | 卡表为部分卡生成 `<key>+` 变体（数值取 `vu`），与基础版同为独立 key，可共存于卡组 | `applyCard` 一律走 `cardVal(card)` 读数值，不写死常量 |
| 随机源 | 洗牌走 `sim.drng`（`seed ^ 0x9e3779b9` 派生），与 `rng` / `trng` 三者隔离 | 抽牌是局中高频行为，若消耗主线 `rng` 会让全部 AI 断言漂移 |

**为什么不改成回合回满墨**：墨在墨战里是「持续回复的能量条」，回合制回满会让实时节奏被切成 15 秒一段（玩家要等回合开始才能出牌），与 RTS 手感冲突。保留持续回复 + 定时抽牌，等于把尖塔的「回合」压缩成一条 6 秒的抽牌脉搏。

### 4.7 同名卡冷却（v1.18）

| 环节 | 实现 | 说明 |
|---|---|---|
| 记账 | `sim.cardCd[owner]` 是 `基础卡key → 到期时刻(sim.t + card.cd)` 的表；`cardPlay` 成功后写入 | 按**基础 key** 记账（升级版 `fire+` 与 `fire` 共享冷却）；到期时刻制免每帧递减 |

## 5. AI 设计

AI 不读私有数据、不作弊（只看公开局面），与玩家走同一 `command` 接口：

```js
InkSim.aiTick(sim, owner, diff)   // 每 diff.interval 秒被 step 调用一次
```

决策序（效用优先级，需求文档 F5）——**先发展、后打仗**的排序经过无头模拟反复调参验证：

1. **扩张**：己方城池 < 地图 60% → 评分选「弱而近」的中立城，多城合击（可集结量 > 驻军 ×0.8 + 2）。
2. **回防**：某城受威胁（来犯敌军 > 驻军 + 2）→ 邻近己城全力增援。
3. **升级兜底**：某城驻军 ≥ 升级消耗 + 5 → 自派一波触发升级（突破发展瓶颈的关键分支）。
4. **前线集结**：向最前线城池（staging）输血，富城与前线驻军差 > 20 才发兵。
5. **进攻**：单一城池集中出兵（多路分批会被逐个击破——无头模拟实测教训），需超过守方驻军 × 难度阈值。
6. **保底强攻**：连续 3 次空转**且城池接近满仓（≥ 九成容量）**时，从最满的城池打最弱的外城，保证对局永不静止。门槛设在满仓是两次模拟调试的结论：门槛过低会让 AI 把城堡抽干到出兵门槛之下，形成「永远凑不齐一波兵」的发展锁死。

失误注入：按 `diff.mistake` 概率把**目标**替换为随机城池（含中立）——失误只影响「打谁」，不绕过阈值产生无脑送兵（否则 AI 驻军均衡点会卡在出兵门槛之下，同样锁死发展）。

### 5.1 AI 用牌（v1.16）

AI 曾经是「绕过牌库直接 `applyCard` 三张固定卡」，v1.16 起与玩家完全同构：

```js
// aiTick 内，每回合最多出一张
if (d.cardLv >= 1 && sim.t > 20 && sim.aiCardCd[owner] <= 0 && rng() < d.cardChance)
  aiPlayCard(sim, owner, d, my, threat);
```

`aiPlayCard` 遍历手牌做三件事，最後只出**收益最高的一张**：

| 步骤 | 规则 |
|---|---|
| 门槛 | `AI_CARD_LV[base] ≤ d.cardLv`（容易 0 = 不用牌；普通 1 = 六类低风险；困难 2 = 全 13 类） |
| 校验 | `canPlay(sim, slot, owner)`——墨量、目标合法性一律与玩家同标准 |
| 目标 | `'own'` 类打**受威胁最重**的己城；`'enemy'/'foe'` 类打 `守军 − 最近己城距离 × nearW` 最大的敌城（**就近优先**）；`'none'` 类（借刀/围魏救赵/墨涌/疾行/神速）自带目标规则 |
| 落袋 | 一律 `cardPlay(sim, slot, target, owner)`：扣墨、`hand.splice`、进弃牌堆或消耗堆、`stats.cardsUsed++`、推 `{type:'card', by:owner}` 事件（玩家侧可见敌方用了什么牌） |

出牌后按牌分级置 `sim.aiCardCd[owner]`（火攻等强牌 40s、护盾 30s、虚弱/增援 20s、疾行/神速 15s）；弱效牌另需 `墨量 ≥ 费用 + 5`（`AI_CARD_KEEP`）才打——统一 40s 冷却 + 无留墨门槛时，AI 会把墨耗在弱牌上，实测胜率 -20pp。

### 5.2 就近扩张与远征闸门（v1.16）

所有「选目标」的评分统一带上**距最近己方城**的距离项：

```js
score = 守军（+ 进攻阈值加成） + nearestDist(sim, owner, 目标) * d.nearW   // 取最小
```

- `nearestDist` = 目标到**任一**己方城的最小距离（原先只用主城 `my[0]`，且权重仅 `1/60`，距离项形同虚设）。
- **远征闸门**：候选先按 `d.expandRange`（中立城）/ `d.atkRange`（敌城）过滤；**范围内有候选就只在该范围内挑**，范围内无候选才放宽到全图——既做到「先吃家门口」，又不会因只看近而锁死发展。
- 保底强攻（连续 3 次空转 + 满仓）同样取「最弱**且**最近」的外城。

**验证口径**：困难 vs 容易 AI 互打 40 局（双方轮换出生点位），困难胜率 ≥ 60%、无一僵局、平均对局时长 ≥ 45s（tools/verify-sim.js 断言项，实测 70% / 0 僵局 / 均值 141s）。

> **v1.16 修正（重要教训）**：`sim.over` 的语义是**胜者阵营**（`!en → over=1`，即 2 号被清空时 over=1）。原断言写成 `hardIsP2 ? over===1 : over===2`，**把「容易的胜率」当成困难胜率来断言 ≥60%**，长期掩盖了「不开牌时困难真胜率仅 ~35%」这一事实。现已修正判据并新增一条 `over` 语义钉死断言，防止再次反向。

## 6. 渲染与输入

### 6.1 渲染分层（每帧全量重绘，自底向上）

| 层 | 内容 | 开销控制 |
|---|---|---|
| L0 背景 | 宣纸底色 + 两团径向晕染 + 远山笔触（预渲染到离屏 canvas，一次生成） | 0（drawImage） |
| L1 城池 | 墨圈主体（径向渐变）+ **等级嵌套环（v1.12：环数=等级）** + 容量环 + **升级进度环** + **城池血条（v1.13：驻军/容量，墨绿→金→朱砂）** + 驻军环字兵 + 驻军数字 + **塔矢量图标（v1.18：炮管/箭矢/四芒星/爪痕）/等级金点/冷却弧/射程圈** + 护盾/虚弱状态环 | ~14 城固定 |
| L2 阵列 | 菱形虚线框 +「屯」 | ≤ 少量 |
| L3 部队 | 每支 Army 画**全量「兵」字方阵**（字号/列数随兵力）+ **每个兵各自的突刺与挥砍弧**（v1.12，上限 24 道） | 上限 300 |
| L4 特效 | 占领晕染双环扩散 / 卡牌浮字 / 火攻墨渍 / **塔火弹道（v1.12：炮塔抛物线、其余直线）** | 短生命周期 |
| L5 指挥层 | 框选矩形 / 瞄准高亮 / 选中金环 + 比例角标 | 按需 |

坐标换算：虚拟地图 1600×900 → canvas，`scale = min(cw/1600, ch/900)`，居中留白；渲染读 sim 状态，不反向写入。

### 6.2 输入（统一 Pointer Events）

- `pointerdown/move/up` 三事件覆盖鼠标与触屏；一律 `getBoundingClientRect()` 取 rect，`sx = MAP_W·scale / rect.width` 换算到虚拟坐标。
- 按压后位移 > 12px 判定为**框选**，否则抬起时判定为**点选/派遣/瞄准**。
- 触屏目标点无需上偏（城池热区半径 ≥ 40 虚拟像素 ≈ 手机上 ~20px，符合 N3 下限，另加 8px 容差）。
- `touch-action: none` + 卡牌按钮独立 DOM，避免与页面滚动冲突。

### 6.2b 卡牌交互（v1.33，杀戮尖塔式）

**卡面只留三要素**：插画 `.inkart` + 名称 `.cn` + 费用角标 `.inkcost`（另保留稀有度框线/角标、升级「＋」、冷却圆徽 `data-cd`、消耗斜切 `data-ex`）。描述 / 冷却秒数 / 消耗文本**一律不出现在卡面**，全部移进 `.inkpop` 详情浮层。
**注意**：`.cd` / `.cc` 两条 CSS **一行未删** —— 结算三选一（`.card.loot`）仍在用它们，删了会让选牌界面丢描述。

**详情浮层**（桌面 `pointermove` 几何命中 / 触屏长按 300ms）：内容 = 卡名 + 稀有度 + 费用 + 冷却秒数 + 目标类型（由 `card.target` 派生，块1 无 `type` 字段故不新增）+ 描述 + 消耗提示。`position:fixed` 且默认 `display:none` —— 不占布局，真机几何量测的「溢出」断言对它免疫。相对**卡牌槽位**定位（不跟光标，跟手会挡棋盘且抖）。

**拖拽状态机**：`idle →(卡栏 pointerdown)→ cardPress →(位移 > cardSlop)→ dragCard →(up)→ idle`

| 环节 | 实现 | 为什么 |
|---|---|---|
| 槽位判定 | **v1.33a 起真实卡面 rect 优先**：`realSlotRects()` 逐卡读 `.card[data-slot]` 的 `getBoundingClientRect`（校验按 `vert` 轴严格递增，全等/乱序判废），`slotAtPoint` / `slotRect` 命中与定位都先走它；读不到（打桩 `querySelectorAll` 恒空、rect 全等）再回退 `HAND_MAX` **几何五等分** | 真实 DOM 才是「点哪张是哪张」的权威 —— `.card` 有 `max-width:96px` 且 `.cards` 是 `justify-content:center`，容器宽于 500px 时卡面居中聚拢，纯五等分从左缘切带整体右漂 `(W−500)/2`，**点第一张卡右半会被算进第 2 槽、弹出邻卡详情**（桌面悬停与触屏长按同路径，v1.33a 修复）；回退路径保证打桩断言确定性（rect 960×540 → 每槽 188px） |
| 事件挂载 | `pointerdown` 挂 `elCards`；`move/up/cancel` 挂 **`window`** | `documentStub.addEventListener` 是 noop；且不用 `setPointerCapture` —— `renderHand()` 会整块重写 `innerHTML`，节点被销毁后靠 window 冒泡照样收得到 |
| 起拖阈值 | `cardSlop()`（桌面 8 / 触屏 12 **CSS 像素**） | 不能复用 `tapSlop()`：那是地图虚拟像素 × `viewK`，打桩下会被放大到 23，不是「手指抖一下」的量级 |
| 跟手替身 | `.inkghost` 挂 `document.body`，底图复用 `cardArtURI()` | 不进 `elCards.innerHTML`（重写碰不到）；不新增第二个 `<i class="inkart">`（断言要求恰好 5 个）；基础态不加 transition，只有回弹 `.back` 才动画 |
| 落点提示 | 合法城池复用瞄牌态的脉动朱砂环（`drawCastle` 的 `aimingValid`，`hlKey` 取 `aim` 或 `dragCard`），光标下那座城再加一道实环；替身 `.ok` / `.bad` | 不新增第二套高亮逻辑 |
| 落点决策 | `dropDecision(slot, v, outOfHand)` 纯函数 | 打桩的 `getBoundingClientRect` 恒覆盖全屏，「拖出手牌区」几何判定失真，测试需能显式喂 `out` |
| 回弹取消 | 替身加 `.back` → 飞回 `slotRect` 中心 → 190ms 后 `remove()` | 非法落点 / 拖回手牌区 / `Esc` / `pointercancel` 四条路径统一 |
| 防重建 | 拖拽态只存 **slot 索引**；`renderHandThrottled` 在 `dragCard` 期间冻结重建 | 墨量整数位变化或冷却秒数跳变就会整块重写 5 张卡 |
| 点按兼容 | 不 `preventDefault`，`click` 仍归 `b.onclick`；拖拽结束置 `dragSwallowClick` 吞一次补发 click | 点击与 `1~5` 快捷键作为**等价入口**完整保留（也是打桩里出牌回归的唯一通路） |
- **键盘**：`1`~`5` 出牌、`Q` 全选己方城池、`空格` 暂停、`Esc` 取消/暂停、`0` 视野复位；`W/A/S/D` **与 `↑↓←→` 等价**，为单兵操控的方向键（见 6.4）。绑定在 `window` 上（不依赖任何元素聚焦），键位走 `dirOf(e)` 归一化（`e.code` → `e.key` → `e.keyCode`），输入框 / 文本域 / `contentEditable` 聚焦时不劫持，输入法组字中不抢键。

### 6.2c 出兵比例条（v1.34）

原「50% / 100%」两颗按钮重构为一条选择条：**读数行（`出兵比例` 标签 + `百分比 — 实际兵力`）+ 滑块（`input[type=range]` 0~100 连续）+ 25/50/75/100 快捷档位**，样式沿用宣纸底 + 墨线框 + 朱砂滑点。

| 环节 | 实现 | 为什么 |
|---|---|---|
| 可用兵力 | `selAvailTroops()` = 选中己方城池 `floor(garrison)` + 阵列 `floor(count)` 合计 | 与 `dispatch` 实际派兵来源一致（在途部队与单兵不走比例），「可用兵力为 0」即「这次点目标什么也派不出去」 |
| 读数口径 | `ratioSendCount(r)` = **逐来源** `floor(驻军 × r)` 再累加 | 与块1 `doSend` 的 `Math.floor(c.garrison * ratio)` 同序同口径 —— 读数就是实派数。注意必须 `garrison × (p/100)`（先除后乘），与块1 一致；先乘后除在浮点下会差 1 兵 |
| 禁用态 | `ratioBarState().off` = 可用兵力为 0 **或** 比例越界 → `.ratio.off` 置灰 + 滑块/档位 `disabled` | 「没选中 / 选中来源已空」时比例无意义；越界值由 `setRatio` 钳进 [0,1]，`dispatch` 发令时再钳一次（双保险） |
| 刷新时机 | 帧循环每帧 `renderRatioBar()` + `setRatio` 即时刷新；内部按 `pct|avail|off` 签名去重 | 选中集一变（点选 / 框选 / 驻军被打光）读数立刻跟上，不等 `updateHud` 的 250ms 节流；无变化不写 DOM |
| 断点适配 | 桌面三行竖排（min-width 192，档位 ≥40px 热区）；竖屏「读数 +（滑块 + 档位）」两行 wrap；**横屏侧栏收成「读数 + 滑块」单行（档位行 `display:none`）** | 横屏侧栏仅 180px 宽且纵向被 5 张卡（min-height 44）挤满，三行版本会把牌堆/提示挤出屏 —— 实测 8 档机型后取舍：连续调节（滑块）保留、快捷档位让位 |
| 打桩 | `__ink` 钩子 `ratio / ratioBar / ratioTxt / ratioCls / ratioRange / selAvail / numFmt` | 桩里 `querySelectorAll` 恒空，事件链测不到 —— 断言走同一入口 `setRatio` 与状态函数，DOM 态（cls/disabled/读数文本）单独断言 |

### 6.4 单兵操控（v1.15，WASD + 鼠标攻击）


「点中哪个兵就操控哪个兵」在 v1.11 只能靠点击目标下达一次性军令；v1.15 补上**持续操控**能力：

| 环节 | 实现 | 说明 |
|---|---|---|
| 操控对象 | `ctrl.id`（被操控的 1 兵部队 id，0 = 无）+ `keys{w,a,s,d}` 按下状态 | 只在 `mode === 'playing'` 生效；开局/暂停/回菜单/兵阵亡即清空 |
| 首次按下 | 无 `ctrl.id` 时，取 selection 里的兵级选择（`s`/`gs`/`ps`），用**与渲染同源**的坐标函数算出该兵当前站位，目标 = 站位 + 方向×160（clamp 到地图内），走既有 `dispatch()` 出队 | 复用 v1.11 的单兵出队链路（含 `pt`/`ph`），出队的仍是「同一个兵」 |
| 认领新部队 | 出队后 `pendingCtrl = true`，下一次 `step` 后取「owner 为本方且 id 最大」的部队记为 `ctrl.id` | 不新增命令类型，纯 UI 侧记账 |
| 持续行走 | `manualTick()` 在主循环里每 0.08s 把目标点推到该兵**前方 160 像素**（`doRetarget` 指向 `pt`） | 按住即走、松开即停；方向为八向（同时按 W+D 走右上，已归一化） |
| 松开 | 所有方向键抬起 → `doRetarget` 到**自身当前位置** → 立即抵达并就地驻扎（1 兵阵列） | 与「点空地 = 列阵屯兵」语义一致；v1.31：驻扎后**自动选中**刚扎下的阵列，可直接按方向键继续，无需再点它 |

**v1.18 扩展——全军接管与点城回防**：

- **接管整支军队**：`manualLaunch` 先扫 selection 里的 `k:'a'`（在途部队）——命中则直接 `ctrl.id = 该部队id`（无需出队认领，`ctrl.acc` 置为 `MANUAL_TICK` 让下一帧立即走第一步）；未命中才走 v1.15 的单兵出队链路。`ctrlArmy()` 本就按 id 查任意部队，多兵部队复用同一条持续行走通路。

## 7. 关键取舍（本期刻意简化项）

| 取舍 | 决定 | 原因 |
|---|---|---|
| 在途部队互战 | **已实现**（应中途追加的需求）：异主部队距离 ≤ 16 即互相湮灭，O(n²) 两两检测受 ARMY_CAP 约束 | 墨色相溶的核心设定；拦截敌方增援成为正式战术 |
| 城池升级 | **自动 + 主动共用一个入口**：增援抵达可自动升级；v1.32 新增城外 `↑` / 快捷键 `E` 主动消耗驻军升级，二者都调用 `upgradeCastle()` | 仍坚持“士兵即经济”，只是把原来只能靠增援触发的升级显式开放给玩家；单一入口防止 20/50 消耗、建塔概率、事件字段在两条路径漂移 |
| 阵列攻防 | 阵列与城池互不打，只被己方再次派遣 | 规则最少化 |
| **过城开战：只互耗 vs 顺势占领（v1.23）** | **选前者**：路过只按 `min(兵力, 驻军)` 互耗，不触发 R3 易主 | 若路过即占领，一支 50 人的队伍去打 A 城的路上会「顺手」吃掉 B 城并**整队被吸收**，任务半路改写——玩家会以为指令失灵。只互耗则语义清楚：路过要付代价、削掉一层守军，但**拿下城池仍需明说打哪座** |
| **过城开战是否豁免护盾（v1.23）** | **护盾免疫路过** | 护盾的语义是「免疫*来犯*」；若连路过都吃消散，一座开盾的城会变成黑洞，把任何途经的队伍全吃掉，远超卡牌定价应有的强度 |
| **屯兵散逸 vs 永久驻守（v1.22）** | **选后者**：移除 `CAMP_DECAY`（原每 5 秒 -1 兵，减到 0 整点消失） | 散逸的初衷是「防无限屯兵」，但代价落在最不该被惩罚的地方——单兵操控松手驻扎 = 1 兵阵列，**约 5 秒就凭空蒸发**，玩家辛苦走位换来的兵白没了（实测反馈即「兵会自己消失」）。且文档自相矛盾：本文件不变量 3 写「散逸至 1 为下限，不归零」，代码却是减到 0 直接 `filter` 删。改为永久驻守后，屯点仍只在**兵派光**或**被敌军打光**时消失，无限蓄兵的克制改由「兵力离开城池即不产兵 + 敌军路过即开战」承担 |
| **伏兵：一次性 vs 持续 12 秒（v1.24）** | **触发一次即清零**（`ambushT/ambushN` 同时归零） | 若 12 秒内所有来犯都吃一发，一座城能白嫖掉一整波进攻，4 墨的定价远超「增援 +25 兵」。一次性则定位清楚：**削掉一层先头部队**，后续仍要靠驻军硬扛 |
| **伏兵 vs 护盾的结算顺序（v1.24）** | **护盾分支先返回，伏兵整段保留** | 开盾的城本来就不会被攻下，若伏兵还跳出来把人吃掉，等于「开了盾还能反打」——与「护盾 = 免疫来犯」的既有语义（v1.23 已定过一次）冲突。护盾先返回也让伏兵不至于被白白浪费 |
| **连弩：临时塔 vs 直接给永久塔（v1.24）** | **临时塔（`tower.temp` + `tempT` 倒计时后拆除）** | 稀有卡 6 墨换一座永久 2 级箭塔，收益远超同价位的「勤王 +18 兵」；到期拆除才能把它的价值锚定在「12 秒的窗口压制」上。已有塔的城不架设，避免覆盖玩家辛苦养起来的永久塔 |
| **新卡是否进默认卡组（v1.24）** | **不进**，只从战利品产出 | AI 与玩家共用同一副 `DEFAULT_DECK`。若新卡进默认卡组，AI 也会拿到，玩家的「跨局累积变强」就被抹平了；不进则新卡纯粹是闯关进度的奖励，AI 侧行为完全不变（既有平衡断言零漂移） |
| **关卡目标：清空优先 vs 目标优先（v1.24）** | **清空优先**（`over` 已定则目标段不改写） | 守城关若在最后一秒被玩家反打清空敌方，却被「时间到了」判成守城成功，语义上都是赢，但反过来——**已经赢下的局被目标段改写判输**才是灾难。清空是最高胜利方式，目标只是在没打完时补一个判定 |
| 失误化 AI | 只替换目标、不绕过阈值 | 「无脑乱送」式失误会让 AI 自我抽干、锁死发展（实测教训） |
| 长按拆分 | 不做，用出兵比例条（v1.34） | 长按与拖框选手势冲突，触屏上弊大于利 |
| **共享 `<defs>` vs 母题函数（v1.19）** | **选母题函数** `M.*`（JS 字符串工厂），每幅插画自包含 | ① 图鉴用 `data-URI` 背景，它是**独立 SVG 文档**，取不到宿主页的 `#id`——共享 defs 在图鉴场景直接失效；② 每次 `innerHTML` 重建会重复插入同名 `id`，文档序第一个胜出，一旦按稀有度着色就会串色；③ 真正占空间的是各卡不同的路径本身，共享 defs 省不下多少。母题函数既能消解重复又零运行时开销 |
| **纸纹用 CSS 渐变 vs `feTurbulence`（v1.19）** | **选 CSS 渐变**（双 radial 云斑 + 1px repeating-linear 帘纹） | 卡面在冷却期**每秒**被 `renderHand` 全量重建一次，逐像素滤镜会重跑 5 次湍流，中低端手机直接掉帧；CSS 背景由浏览器栅格化缓存，且不依赖 `#id`，可同时用于内联 SVG 与 data-URI 两种场景 |
| **手牌插画作水印 vs 正式图区（v1.19）** | **手牌水印（absolute + `--art-op`）、结算三选一正式图区（`--art-loot-h`）** | 手牌卡面只有 96×64，`cn/cd/cc` 三件套已占满高度，再插图区会撑高卡栏 → 抬高 `--stage-reserve` → 挤小地图。水印零高度代价，重排开销近 0；结算卡宽约 170px，放得下正式图区 |
| **单兵操控只认物理键盘 vs 屏内方向键（v1.20）** | **补上屏内十字方向键**（`.dpad`，`.stage` 内与 canvas 平级的 DOM 覆盖层） | 内嵌预览面板（webview 常吞 `keydown`）、手机触屏这两种环境下 `WASD` 等于完全不可用——单兵操控是 v1.9 以来的核心卖点，却有一半环境用不了。方向键与 `onKeyDown` **共用 `manualStart()` 一条链路**，不是另写一套操控逻辑，两边永远同构 |
| **认领「id 最大的部队」vs 认领「按下前不存在的新部队」（v1.20）** | **选后者**，出队前先快照 `ctrl.pendKnown` | `manualTick` 跑在 `Sim.step` **之前**，单兵出队的命令要等下一步才生成新部队——旧逻辑此刻认领到的「id 最大」仍是原大军，按一下方向键就把整支 20 人大军一起劫持了（实测复现）。快照差集是唯一不依赖时序的判据 |
| **点击部队选整支 vs 仍选单个兵（v1.20）** | **仍以单个兵优先**，只在 `hitSoldier → hitCastle → hitCamp` 全落空后才兜底 `hitArmy` | 兵级指挥（v1.9）要求「点谁是谁」，不能因为想选整支就牺牲单兵精度；兜底放在城池/阵列之后，部队停在城边时不会抢掉「点城池」。真正「接管整支」的明路是**框选**或**方向键中心「全」** |
| **敌方出牌用横幅 vs 只飘卡名（v1.20）** | **横幅 + 目标城池飘字/圆环 + 专属下行音三层** | 原来只有地图顶部一个 1.4 秒卡名，没说谁打的、打的是谁，多方混战时 2/3/4 号还一律黛青；现在事件带 `target`，提示直接落在被打的那座城上，且提示音与己方出牌的上扬音可盲听区分 |
| **竖屏 `space-between` vs 舞台 `margin:auto` 居中（v1.21）** | **选后者**：顶栏贴顶、卡栏贴底、舞台在中间垂直居中 | 16:9 地图受宽度封顶，竖屏纵向必然富余（390×844 上空白曾达 54%）；`space-between` 把这块空白均分成上下两块死白、棋盘孤零零悬在正中。舞台 `margin:auto` 让空白仍均分到地图上下，但棋盘与顶栏/卡栏的关系稳定可预期 |
| **横屏卡栏贴底一行 vs 右侧竖排侧栏（v1.21）** | **选右侧竖排侧栏**（`fixed`，`width:180px`，脱离文档流） | 横屏棋盘宽度 = `(屏高 − 预留) × 1.778`，卡栏贴底时预留 174px，棋盘只有 384 宽（占屏宽 45%，左右各空 230px）；侧栏化后预留只剩顶栏 84px，棋盘 544（+42%）。代价：`measureStageReserve` 要用 `matchMedia` 与 CSS 断点**逐字同源**地判断侧栏态，且舞台须靠左排（棋盘由高度封顶时可能宽于让出的宽度，居中会压到侧栏） |
| **提示条高度自适应 vs 钉死（v1.21）** | **钉死 + `overflow:hidden`** | `.hint` 在卡栏内，文案每随选中状态变化；高度自适应时卡栏跟着涨，`ResizeObserver` → `relayout` → **棋盘实时跳动**（平板上实测位移 53px）。钉死后卡栏高度恒定，棋盘稳定 |
| **手机竖屏隐藏提示 vs 显示（v1.21）** | **显示**（卡栏第一行，固定 42px） | 原先 `≤700px` 与横屏都 `display:none`，实测整个手机端**完全看不到操作指引**（0×0）；竖屏纵向富余，完全放得下 |
| **难度四档：改 key vs 只换中文标签（v1.25）** | **只换标签**：`DIFF` 的 `easy/normal/hard` 数值一字不动，只加 `master`；UI 层用 `DIFF_LABEL` 映射成 休闲/标准/困难/宗师 | 改 key 或调既有数值会让全部平衡断言（AI 分层采样、闯关胜率、A/B 实测）整体漂移，等于把已经调好的三档推翻重来。加一档 + 换标签是零成本的最小改动 |
| **自定义参数：新增字段 vs 复用 `sim.mods`（v1.25）** | **复用**：`capMul`/`prodMul` 直接乘进已有的 `sim.mods.cap/.prod`，`inkStart` 只在建局处改初值 | `mods` 本来就是「日卡被动 → 全局修正」的通道，语义完全吻合；新增字段要同时改快照编码、联机同步与既有断言。不传 `custom` 时与 v1.24 逐字节等价 |
| **战报落盘 vs 只留内存（v1.25）** | **只留内存** | 曲线 600 点 × 4 阵营 ≈ 数十 KB，若持久化会挤占本就不宽裕的本地配额，而战报「看完即弃」的使用频率远低于存档与成就。内存态已能满足「打完立刻复盘」 |
| **存档：中局快照 vs 种子 + 配置（v1.25）** | **种子 + 配置** | `sim` 里带着 `rng/trng/drng` 三个函数与互相引用，JSON 化不可靠、反序列化后行为还可能与原局不一致；而「同种子 + 同配置」是**可复现的最小充分条件**（实测两次复现地图逐点相同）。代价：不能从半局续打——这是可接受的取舍 |
| **引导改写 `mode` vs 正交开关（v1.25）** | **正交**：新增 `panel` 子状态与 `tut` 开关，`mode` 四态语义一字不动 | `mode` 决定「跑不跑模拟」，是 `loop()` 里所有分支的判据；让引导挤进去等于给每条分支多加一个条件。正交后既有分支零改动，引导期间 mode 可以是 menu 也可以是 playing |
| **客机断粮：快照补字段 vs 客机自己推算（v1.26）** | **补字段**（`fx`/`pt` 两个效果数组 + 城池行尾部追加四字段） | 客机航位推算走 `Sim.armySpeed`，它要读 `slowT`；快照不带它，客机在断粮期间按原速推算、位置持续超前，每 100ms 再被快照硬拉回一次 = 肉眼可见抖动。字段一律**尾部追加**，新旧版本可互解 |
| **联机码：整份 SDP vs 裁剪 + 令牌 + 压缩（v1.26）** | **裁剪 + 令牌 + base64url**，支持时再叠 `deflate-raw` | 原码两三千字符，微信里会被截断。**无损**是硬要求（少一个候选就少一条通路），所以只做可逆变换：白名单裁剪（丢掉数据通道用不到的行）、令牌替换（高频前缀换单字符）、base64url（去填充 + URL 安全）。实测缩短 37%~60% |
| **令牌作用域：整个载荷 vs 只作用于 SDP（v1.26）** | **只作用于 SDP**（先替换、再包 JSON） | 令牌表里用了 `{` `}` 等字符，若先包 JSON 再替换，JSON 自己的括号会被一起换成 `a=candidate:`，解出来是非法 JSON（实测踩到）。先替换再包 JSON 则零歧义 |
| **失联判定：只靠 `onclose` vs 心跳 + 计时（v1.26）** | **心跳 + 计时**：每秒 `pg`/`po`，连续 4 秒无下行包即判失联 | `DataChannel.onclose` 在异常网络（拔网线、切后台、NAT 老化）下可能**长时间不触发**，只靠它永远发现不了「假在线」——对局会在无人知晓的情况下继续跑。心跳顺带把 RTT 测出来给玩家看 |
| **失联后继续跑 vs 暂停 + 宽限（v1.26）** | **暂停 + 10 秒宽限** | 主机是对局唯一模拟者，若对手掉线后主机继续推进，回来就是一片废墟——技术上合法、体验上是背叛。暂停 + 宽限把「掉线」变成一次可恢复的中断 |
| **ICE `disconnected` 是否立刻判死（v1.26）** | **不判死**，交给心跳宽限；只有 `failed`/`closed` 立刻报原因 | `disconnected` 多为瞬时抖动（切 Wi-Fi、休眠唤醒），立刻终止会误杀大量可恢复的连接；`failed`/`closed` 才是确定性终态 |
| **客机暂停：直接生效 vs 请求制（v1.26）** | **请求制**（`pausereq`，决定权在房主） | 客机若能单方面冻结对局，可以靠反复暂停拖时间、也可以在主机不在时把局面锁死。请求制保留了客机的诉求通道（此前客机连按钮都是隐藏的），又不让渡控制权 |
| **再战：单边发车 vs 双向确认（v1.26）** | **双向确认** | 此前客机一按「再来一局」就把主机直接拽进新局，而主机可能还在看战报或选战利品。改成本地只登记意愿、双方都点头才发车，并给 20 秒无响应提示 |
| **触屏阈值：虚拟像素写死 vs CSS 像素标定（v1.28）** | **CSS 像素标定 + 粗指针放大** | 手机竖屏 cover 下 1 CSS px ≈ 2~3 个地图虚拟像素，写死的「点按位移 14 / 兵命中 10」在真机只有 5~7 CSS px——点不中兵、轻抖就误判拖拽出兵。改 `mapPerCss()` 换算 + 触屏容差放大 + **落指命中**（胖手指补偿：按下到抬起常见 10~20px 滑动，按抬起点判定会落空）；桌面语义不变，打桩（mapPerCss=5/3）断言逐位不漂 |
| **WASD 起步条件：只认「点中的兵」 vs 认「选中的己方单位」（v1.29）** | **认选中的己方单位（城池 / 阵列 / 兵 / 部队），无选中时接管最近的己方在途部队** | 实测输入到反馈的因果延迟只有 32 ms（起步）/ 32~64 ms（改向）/ 0 ms（松开），「不跟手」根本不在延迟上——真因是**入口断掉**：`manualLaunch` 要求先点中一个兵，而电脑上一个驻城环兵的命中直径只有约 7 CSS px，手机端屏内方向键在选中城池时压根不显示。用户最自然的「点自己的城 → 按方向键让它往那边走」此前只会弹提示 + 一声错误音。改成从最好点的目标（城池/阵列）就能起步，派兵后自动接管，之后 WASD 持续改向；`nearestOwnArmy()` 兜底让「什么都没选中」也不再是死路 |
| **基准 fit：contain vs cover（v1.27）** | **cover（铺满）** | 竖屏把画布比例放宽到 1.35 后，contain 会在上下留死白——多出来的画布高度一点没变成地图，等于白改。cover 才让线性尺寸真的 +32%。代价是两侧各裁约 12%，由缩略图 + 双指平移补偿。桌面 / 横屏恒为 16:9，两者相等，**既有渲染断言逐像素不变** |
| **缩放平移：单指复用 vs 只走双指（v1.27）** | **只走双指** | 单指拖动在本作里是「框选 / 派遣」核心操作，复用成平移会让新手拖不出兵（也可以做成长按切换，但那要额外一条状态机且更难发现）。双指是移动端地图的标准手势，零学习成本，且天然不与单指冲突 |
| **裁切后靠什么补全图感知：缩略图 vs 边缘箭头（v1.27）** | **左下角缩略图**（全图城池点 + 朱砂视口框） | 边缘箭头只告诉你「那边有东西」，缩略图直接告诉你「在哪、还有多少」。只在 `viewMoved()` 时画 —— 默认全览时它是纯噪声 |
| **新手难度：更保守 vs 更敢打（v1.27）** | **更敢打但更不准**（minPool 5 / buffer 0.5 / mistake 0.6） | 反直觉但实测明确：把敌人做成「缩在家里攒兵」的龟壳（初版 buffer 1.0 / minPool 16），弱玩家胜率反而从 48% 掉到 42% —— 厚壳才是新手最难啃的。改成低门槛出兵后家里留不住兵，弱玩家胜率 64%，且我方被占城数 3.5 → 2.2（压力也更小） |
| **新手关：加一档难度 vs 只调关卡参数（v1.27）** | **加 `DIFF.novice` 一档**（既有的 easy/normal/hard/master 一字不动） | 只调城池数 / 敌数改不动「敌人性格」，而手感差异几乎全在性格上。新增一档是**纯加法**，既有难度与平衡断言零漂移 |
| **难度档位：4 档 vs 5 档（v1.27）** | **5 档**（新增「入门」） | 入门档只给闯关前两关 + 快速对战可选，既给新手一个明确入口，又用断言锁住「入门只用于前两关」，不稀释中后期难度 |
| **联机战绩：并入 `record` vs 独立 `netRec`（v1.26）** | **独立记账**（`ink.netrec`） | 好友对战可无限重开，若计入单机连胜 / 生涯 / 成就，等于开了一条刷分通道（且 `record.streak` 会喂给「三连捷」成就）。分开后两边口径各自自洽：单机走 `record` + `life`，联机只走 `netRec` |
| **等待室规则是否提供难度选项（v1.26）** | **不提供** | PVP 双方都是人、没有 AI，而 `diff` 在块1 里只影响 AI 的决策参数——放一个选了没有任何效果的控件属于误导。可选项改为**地图 / 节奏 / 限时**三个真实生效的旋钮 |
| **引导遮罩：`clip-path` 挖洞 vs 四面 div 围洞（v1.25）** | **四面 div 围洞** | 单个 `polygon` 无法表达两个子路径（挖洞需要 evenodd 两条闭合环），`clip-path: path()` 在老一些的 WebView 上支持度不稳；四个 div 是零成本、零兼容风险的写法，且便于逐面调试 |
| **塔索敌：只扫在途部队 vs 在途 + 阵列统一候选（v1.32）** | **统一候选并按距离取最近** | 阵列本质仍是敌方兵力。旧逻辑只扫 `armies`，敌军一落地转 `Camp` 就从塔的世界里消失，四种塔同时“失明”。统一 `towerHit/towerSplash` 后，射程、冷却、伤亡与事件只有一套语义 |
| **升级入口与驻军热区重叠（v1.32）** | `upChipOf()` 放在驻军最外环之外，右边界自动翻左；pointerup 中明确按钮优先 | 旧试做把徽章放在 `castleR+22`，而第一圈驻军在 `castleR+13`，两者圆心只差 9px，正好落进 `hitSoldier` 的 10px 命中范围；优先点兵时入口偶发失效，优先入口时又会抢兵。先做几何隔离，再给显式按钮优先，才能同时保证两条交互 |
| **升级成功后的选择清理：全清 vs 定向清理（v1.32）** | 只移除目标城的 `gs`（驻城单兵）选择，其它城池/阵列/部队选择保留 | 入城的那名兵已被消耗，继续保留会成为失效指针；但全清会破坏框选/多选的既有行为。定向过滤是影响面最小的方案 |

## 8. 联机实现（v1.1 好友对战）

架构预留的三个前提（确定性时间轴、因果链=命令流、逻辑渲染分离）在本期兑现为 **1v1 好友对战**，采用「主机权威状态同步」而非帧同步：

| 决策 | 内容 | 理由 |
|---|---|---|
| 传输 | WebRTC DataChannel P2P | 纯前端可联机；信令用「邀请/应答码」人工交换（ICE 收集完毕的 SDP base64，可编码进 `?join=` 链接），静态托管（GitHub Pages）无需自建服务器 |
| 同步 | 主机权威：主机是唯一模拟者，每 100ms 广播压缩快照（数组化，约 1~2KB/包）；客机不跑模拟，写入本地镜像并做部队航位推算（120px/s×两帧间隔） | 免除跨设备浮点确定性难题；PVE 的模拟核心零改动复用（`step` 只在主机调用） |
| 指令 | 客机派遣/卡牌/升级 → `{t:'cmd'}` → 主机经 `Sim.command / cardPlay(owner=2)` 执行 → 下个快照回传结果；`castleUp` 不信任线上 `cmd.owner`，主机强制重建为 owner=2 再校验 | 玩家与 AI、远程玩家共用同一命令接口；主机权威防止客机伪造 owner=1 消耗房主驻军 |
| 视角 | UI 层以 `mySide`（1=主机 2=客机）替换全部 owner=1 硬编码：HUD/手牌 `hands[mySide]`/选中校验/派遣 owner/胜负 `over === mySide` | 同一份 UI 代码服务 PVE 与联机双方 |
| 模拟层 | `hands: {1:[],2:[]}` 双手牌，`cardPlay/canPlay` 增加 owner 参数（默认 1，PVE 行为不变） | 客机手牌由快照同步，出牌指令交主机结算 |
| 生命周期 | 房主暂停/继续广播；「再来一局」主机换种子重开并广播 `start`（双方 `createGame` 同种子 → 同图，城池 id/坐标天然对齐，快照无需传坐标）；断开即终止并弹「断·连」 | 最小状态机 |
| 等待室（v1.13） | 连接建立后先进等待室：`{t:'info'}` 交换战绩、`{t:'ready'}` 同步准备态，双方 ready 后 3 秒倒计时由主机广播 `start`；中途断开按 `wasLobby` 分支回菜单而不弹「断·连」 | 把「连上就开局」改成有仪式感的对战前厅，同时给双方确认带宽/延迟的机会 |
| **短联机码（v1.26）** | 信令码由「整份 SDP 的 base64」改为 `sdpMin`（白名单裁剪）→ `tok`（高频前缀换单字符）→ `b64u`（base64url）；支持时再叠 `deflate-raw`。码首字符 `z`/`s`/其余 区分压缩码 / 裁剪码 / 旧版码 | 原码动辄两三千字符，微信里会被截断、手抄更不可能。实测缩短 37%（裁剪）~ 60%（压缩）。**令牌必须先作用在 SDP 上再包 JSON**，否则令牌里的 `{` `}` 与 JSON 括号撞车 |
| **心跳与断线宽限（v1.26）** | 每秒 `pg`/`po` 测 RTT；`netMiss` 累计无下行包秒数，`NET_MISS=4` 判失联 → `mode='paused'` + `NET_WAIT=10` 秒重连宽限；`netBindDrop` 只在 ICE `failed`/`closed` 时立刻报原因 | `DataChannel.onclose` 在异常网络下可能长时间不触发，只靠它永远发现不了「假在线」。失联即暂停，主机不能趁对手掉线单方面推进 |
| **客机本地预测（v1.26）** | 下令后立刻在本地生成一支半透明影子部队（950000+ 号段，`ghost:1`，alpha 0.42），真身随下一份快照覆盖 | 「一个 RTT + 100ms 才看到反应」的空档最伤手感。影子不进任何判定（框选/命中/选中一律跳过），纯表现 |
| **连续指令：驻扎后是否保留选中（v1.31）** | **只在操控链路保留**（`dispatch(…, keep=true)` + `ctrl.settle` + `manualSettle()`），一次性军令仍「下达即清空」 | 「移动 → 驻扎 → 再移动」每轮都要重新点一次阵列，手机上那点热区根本点不准，操控链路等于断的。但不能无差别保留：RTS 里「派完兵即清空」是防止误触二次派遣的护栏，点目标派遣 / 回防 / 点空地列阵若也保留，下一次点目标就会变成「旧源 + 新源齐发」。故用 `keep` 参数把两条链路分开；`settle` 标志区分「主动松手驻扎」与「被歼灭」，后者不接管任何阵列 |
| **方向键的键位取值：`e.code` 单一来源 vs 三级回落（v1.30）** | **`dirOf(e)` 三级回落**：`e.code` → `e.key`（大小写不敏感，认 `ArrowX`）→ `e.keyCode`（37~40 / 87,65,83,68） | 只认 `e.code` 就是「物理方向键完全没有分支」这个 bug 的成因（键盘上 ↑↓←→ 按下去只有浏览器默认的滚动页面）。反过来只认 `e.key` 会被输入法（`Process` / `keyCode 229`）、Shift 大写、非 QWERTY 布局坑到；`e.code` 是物理键位、不受这些影响，故它优先。三级回落让「虚拟键盘 / 老浏览器只给 `e.key`」的环境也能用，同时 `isComposing` 时直接放行给输入法，`onKeyUp` 用同一套归一化保证不会「按下算方向、抬起不算」而卡住 |
| **再战双向确认（v1.26）** | `netAgain{me,foe,t}`：任一方点「再来一局」只登记，双方都点头才由房主发车；`NET_ACK=20` 秒无响应给提示 | 此前客机一按就把主机拽进新局，主机可能还在看战报/选战利品 |
| **战绩口径（v1.26）** | 单机走 `record` + `life`；联机只走 `netRec`（`ink.netrec`），结算页展示「联机战绩」 | 好友对战可无限重开，若计入单机连胜 / 生涯 / 成就会变成刷分通道；分开记账后两边口径各自自洽 |
| **指令权威校验（v1.35）** | 主机收到 `cmd` 后**按固定阵营（G=2）重建整条指令**（`send` / `retarget` / `split` / `allout` / `castleUp` / `card`），只取网络包里的**参数**（`from`/`to`/`ids`/`armyId`/`ratio`/`slot`/`target`），`owner` 与 `type` 一律不采信；`ratio` 钳进 [0,1] | v1.35 之前 `send`/`retarget`/`split` 是把 `d.cmd` 原样丢进 `Sim.command`，客机改包即可伪造 `owner:1` 调遣房主的兵（只有 `card`/`castleUp`/`allout` 强制了 2 号）。块1 各指令本就按 `owner` 校验城池/阵列/部队归属，主机只要**不采信 owner** 就天然免疫，无需在块1 再加一层 |

### 8.1 远期帧同步演进

若要 migrate 到帧同步：`sim` 已是固定步长 + 种子随机（`mulberry32` 仅用 `Math.imul/add/shift`，跨设备确定）+ 命令驱动——把「主机广播快照」替换为「双端交换带帧号的命令流 + 本地确定性重放」即可，浮点结算（`Math.sqrt` 为 IEEE 正确舍入）风险可控；届时再按需引入定点数。
