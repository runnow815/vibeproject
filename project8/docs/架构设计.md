# 墨战（project8）架构设计

> 配套：[需求文档](./需求文档.md) · [可视化原型](./prototype.html)
> 本文描述 v1.0 单机人机版的实现架构，并说明为未来联机预留的演进路径。

---

## 1. 技术选型

| 维度 | 选型 | 理由 |
|---|---|---|
| 形态 | 单文件 `inkwar.html`（CSS+HTML+JS 内联） | 仓库铁律：零依赖、零构建、双击即玩（见 CLAUDE.md） |
| 渲染 | Canvas 2D 全量重绘 | 实体为大量圆点/圆环，Canvas 足够且省事；不需要 DOM 动画级联 |
| 逻辑 | 原生 JS（`'use strict'` + IIFE） | 与 project1~7 一致 |
| 音效 | WebAudio 振荡器合成 | 无音频文件，`Sound.tone()` 基础合成器 + 各事件音效方法 |
| 存档 | localStorage（前缀 `ink.`） | 闯关进度/最快胜利/音效开关/上次配置 |
| 模拟 | **固定步长 1/30s + 命令驱动** | 逻辑确定性时间轴；渲染只读状态，二者解耦 |

**为什么不做 ECS / WebSocket / 定点数**：单机人机不需要跨设备确定性（浮点即可）、单位规模 ≤300（O(n) 结算足够）、无后端。Cocos/Laya、Go 后端、帧同步服务器均为原版墨战的工程语境，本期仅保留**可演进的结构**（见第 8 节）。

## 2. 文件内分层（双 script 块，沿用 project7 骨架）

```
inkwar.html
├── <style>                CSS 变量 / .stage 三重约束响应式 / HUD / 卡牌栏 / overlay / 4 组媒体断点
├── <body>                 .wrap = .stage(canvas#board + .overlay) + .side(说明面板)
├── <script> 块1：纯逻辑层（可测试）
│    └── IIFE → window.InkSim = { CFG, CARDS, LEVELS, mapGen, createGame, step, command,
│                                 cardPlay, checkEnd, aiTick } + module.exports（Node 验证用）
└── <script> 块2：IIFE UI 层
     ├── ===== DOM =====          getElementById 集中引用
     ├── ===== 音效 =====         Sound（惰性 AudioContext / tone / 事件音效 / 开关）
     ├── ===== 状态 =====         ui state：mode('menu'|'playing'|'paused'|'over') / 选中集 /
     │                            比例 / 瞄准卡 / 手牌 / 存档
     ├── ===== 流程 =====         showOverlay / startGame(config) / endGame / pause
     ├── ===== 输入 =====         pointer 统一处理（rect 缩放）：点选/框选/派遣/瞄准
     ├── ===== 卡牌 UI =====      卡槽渲染 / 瞄准模式 / 墨量不足反馈
     ├── ===== 渲染 =====         draw()：山水宣纸背景 → 城池 → 阵列 → 部队 → 特效 → 框选/瞄准
     ├── ===== HUD =====          updateHud()（250ms 节流）
     └── ===== 主循环 =====       rAF：累积器喂 InkSim.step(1/30)，永远 draw()
```

**分层铁律**：块1 不触碰任何 DOM/WebAudio，输入输出均为纯数据——这是 N7（逻辑可测）与第 8 节（联机演进）的共同前提。

## 3. 核心数据结构

```js
// ---- 常量（需求文档 2.4 数值表的代码化，二者同步维护）----
CFG = {
  MAP_W: 1600, MAP_H: 900,       // 虚拟地图尺寸，渲染等比缩放
  SPEED: 120,                    // 行军速度（虚拟像素/秒）
  MIN_DIST: 240,                 // 城池最小间距
  CLASH_R: 16,                   // 在途遭遇半径（墨色相溶，需求 R8）
  INK_MAX: 10, INK_START: 3, INK_REGEN: 0.25,
  CAPTURE_INK: { enemy: 2, neutral: 1 },
  CAMP_DECAY: 5,                 // 阵列每 5 秒散逸 1 兵
  SHIELD_T: 8, WEAK_T: 10, RUSH_T: 10,
  ARMY_CAP: 300,                 // 部队实体上限（N4）
  REINFORCE_N: 25, SURGE_N: 8, FIRE_KILL: 0.4,
}
LEVELS = [                        // 下标 = 等级-1（数值与需求文档 2.4 同步）
  { rate: 0.7,  cap: 35,  up: 20 },
  { rate: 1.2,  cap: 70,  up: 50 },
  { rate: 1.8,  cap: 110, up: null },   // 封顶
]

// ---- 实体 ----
Castle = {
  id, x, y,
  owner: 0 | 1..4,      // 0=中立，1=玩家，2..4=AI（颜色阵营）
  level: 1..3, garrison: float,
  shieldT: 0, weakT: 0, // 增益/减益倒计时
  flashT: 0,            // 占领晕染动画计时（纯表现，放在 sim 是为了回放一致性）
}
Army = {                // 在途部队：从 from 到 to 的直线行军流
  id, owner, count,
  x, y, tx, ty,         // 当前位置与目标点
  tKind: 'castle'|'pt', // 目标类型（城池 / 空地列阵点）
  tid,                  // 目标城池 id（tKind='pt' 时为 -1）
  srcId,                // 出发城池 id（围魏救赵「折返」用；-1 = 出自阵列）
  hx, hy,               // 出发点
}
Camp = {                // 阵列（屯兵驻点）
  id, owner, x, y, count,
  decayAcc: 0,          // 散逸累积器
}
Card = { key, cost, needTarget }   // 8 张，见需求文档 2.3

GameState = {
  t: 0,                          // 模拟时间（秒，固定步长推进）
  castles: [], armies: [], camps: [],
  ink: [...],                    // 各阵营墨量
  hand: [...], deckFn,           // 玩家手牌与摸牌函数
  effects: { rushT: 0 },         // 全局增益
  stats: { captured: 0, cardsUsed: 0 },
  over: 0 | 1 | 2 | 'draw',      // 0=进行中 1=玩家胜 2=玩家败
  rngSeed,                       // 种子随机（mapGen / AI 失误 / 摸牌），见第 8 节
}
```

**数值边界**：`garrison` 为 float（产兵累积），但**结算时一律 `Math.floor`** ——战斗以整数兵力发生，避免「0.4 个兵打赢 0.3 个兵」的观感问题；显示时同样取整。

## 4. 模拟循环与命令系统

### 4.1 固定步长推进

```js
// UI 层主循环
loop(t) {
  acc += min(50, t - last);            // dt 钳制，防后台切回大跳帧
  while (acc >= STEP && mode === 'playing') {
    InkSim.step(sim, STEP);            // 每步固定 1/30s，一次只推一步
    acc -= STEP;
  }
  draw(); requestAnimationFrame(loop);
}
```

单步内顺序（需求文档 F2）：**命令队列 → 产兵 → 部队推进/抵达结算 → 在途遭遇（异主湮灭）→ 阵列散逸 → 增益倒计时 → 墨量回复 → AI → 胜负判定**。命令在步首执行，保证「本帧点击、本帧生效」。

### 4.2 命令接口（玩家与 AI 共用）

```js
// 唯一的模拟状态变更入口——UI 与 AI 都只“下命令”，不直接改数据
InkSim.command(sim, { type: 'send', fromIds: [...], to: castleId | {x,y}, ratio: 0.5|1 })
InkSim.cardPlay(sim, { key: 'fire', targetId? })   // 已校验墨量；不合法返回 false

// send 内部：每座来源城 floor(garrison × ratio) 兵 → 生成 Army（出兵城 garrison 同步扣减）
// to 为 {x,y} 时：出城兵最后 1 个 Army 抵达点生成/并入 Camp（阵列）
```

这个收口是刻意设计：**模拟的因果链 = 命令流**。录下一局所有命令 + 种子即可完整回放，也是未来帧同步所需的全部输入。

### 4.3 战斗结算（F3 的实现要点）

- 抵达己方城：`garrison = min(garrison + count, cap)`；若 `garrison >= up 且 level < 3` → 扣 `up` 升级（每步最多升 1 级，余量留到下一步）。
- 抵达敌/中立城：护盾生效则部队消散；否则 `count > garrison` → 易主（驻军 = 差值并**按新城池容量封顶**，等级保留，占领方墨量 +2/+1），否则 `garrison -= count`。
- 抵达阵列：同主并入，异主**不交互**（本期取舍，见第 7 节）。
- **在途遭遇（墨色相溶）**：推进后对所有 Army 做同帧两两检测，异主且距离 ≤ `CLASH_R`（16）→ 双方按 `min(countA, countB)` 互相湮灭，归零者移除（不变量 count ≥ 1 由此维持），并推送 `clash` 事件供表现层画墨晕。复杂度 O(n²) 但 n ≤ 300（ARMY_CAP），每步 ≤ 4.5 万次距离判定，性能无忧。

## 5. AI 设计

AI 不读私有数据、不作弊（只看公开局面），与玩家走同一 `command` 接口：

```js
InkSim.aiTick(sim, owner, diff)   // 每 diff.interval 秒被 step 调用一次
```

决策序（效用优先级，需求文档 F5）——**先发展、后打仗**的排序经过无头模拟反复调参验证：

1. **扩张**：己方城池 < 地图 60% → 评分选「弱而近」的中立城，多城合击（可集结量 > 驻军 ×0.8 + 2）。
2. **回防**：某城受威胁（来犯敌军 > 驻军 + 2）→ 邻近己城全力增援。
3. **升级兜底**：某城驻军 ≥ 升级消耗 + 5 → 自派一波触发升级（突破发展瓶颈的关键分支）。
4. **前线集结**：向最前线城池（staging）输血，富城与前线驻军差 > 20 才发兵。
5. **进攻**：单一城池集中出兵（多路分批会被逐个击破——无头模拟实测教训），需超过守方驻军 × 难度阈值。
6. **保底强攻**：连续 3 次空转**且城池接近满仓（≥ 九成容量）**时，从最满的城池打最弱的外城，保证对局永不静止。门槛设在满仓是两次模拟调试的结论：门槛过低会让 AI 把城堡抽干到出兵门槛之下，形成「永远凑不齐一波兵」的发展锁死。

失误注入：按 `diff.mistake` 概率把**目标**替换为随机城池（含中立）——失误只影响「打谁」，不绕过阈值产生无脑送兵（否则 AI 驻军均衡点会卡在出兵门槛之下，同样锁死发展）。

**验证口径**：困难 vs 容易 AI 互打 40 局（双方轮换出生点位），困难胜率 ≥ 60%、无一僵局、平均对局时长 ≥ 60s（tools/verify-sim.js 断言项，实测 63% / 0 僵局 / 均值 61s / 40 局累计 63 次在途遭遇战）。

## 6. 渲染与输入

### 6.1 渲染分层（每帧全量重绘，自底向上）

| 层 | 内容 | 开销控制 |
|---|---|---|
| L0 背景 | 宣纸底色 + 两团径向晕染 + 远山笔触（预渲染到离屏 canvas，一次生成） | 0（drawImage） |
| L1 城池 | 墨圈主体（径向渐变）+ 等级虚线环 + 驻军数字 + 护盾/虚弱状态环 | ~14 城固定 |
| L2 阵列 | 菱形虚线框 +「屯」 | ≤ 少量 |
| L3 部队 | 每支 Army 画 3~5 个墨点队列（沿速度方向排布，大小随 count 增减） | 上限 300 |
| L4 特效 | 占领晕染双环扩散 / 卡牌浮字 / 火攻墨渍 | 短生命周期 |
| L5 指挥层 | 框选矩形 / 瞄准高亮 / 选中金环 + 比例角标 | 按需 |

坐标换算：虚拟地图 1600×900 → canvas，`scale = min(cw/1600, ch/900)`，居中留白；渲染读 sim 状态，不反向写入。

### 6.2 输入（统一 Pointer Events）

- `pointerdown/move/up` 三事件覆盖鼠标与触屏；一律 `getBoundingClientRect()` 取 rect，`sx = MAP_W·scale / rect.width` 换算到虚拟坐标。
- 按压后位移 > 12px 判定为**框选**，否则抬起时判定为**点选/派遣/瞄准**。
- 触屏目标点无需上偏（城池热区半径 ≥ 40 虚拟像素 ≈ 手机上 ~20px，符合 N3 下限，另加 8px 容差）。
- `touch-action: none` + 卡牌按钮独立 DOM，避免与页面滚动冲突。

## 7. 关键取舍（本期刻意简化项）

| 取舍 | 决定 | 原因 |
|---|---|---|
| 在途部队互战 | **已实现**（应中途追加的需求）：异主部队距离 ≤ 16 即互相湮灭，O(n²) 两两检测受 ARMY_CAP 约束 | 墨色相溶的核心设定；拦截敌方增援成为正式战术 |
| 城池升级 | 增援自动升级，无手动按钮；AI 另有「自派升级」分支 | 减少操作层级，符合「士兵即经济」的墨战设定 |
| 阵列攻防 | 阵列与城池互不打，只被己方再次派遣 | 规则最少化；散逸机制（5s -1 兵）防无限屯兵 |
| 失误化 AI | 只替换目标、不绕过阈值 | 「无脑乱送」式失误会让 AI 自我抽干、锁死发展（实测教训） |
| 长按拆分 | 不做，用 50%/100% 按钮 | 长按与拖框选手势冲突，触屏上弊大于利 |
| 浮点兵力 | 结算/显示取整，占领溢出按容量封顶 | 见第 3 节；单机无需定点数 |

## 8. 联机实现（v1.1 好友对战）

架构预留的三个前提（确定性时间轴、因果链=命令流、逻辑渲染分离）在本期兑现为 **1v1 好友对战**，采用「主机权威状态同步」而非帧同步：

| 决策 | 内容 | 理由 |
|---|---|---|
| 传输 | WebRTC DataChannel P2P | 纯前端可联机；信令用「邀请/应答码」人工交换（ICE 收集完毕的 SDP base64，可编码进 `?join=` 链接），静态托管（GitHub Pages）无需自建服务器 |
| 同步 | 主机权威：主机是唯一模拟者，每 100ms 广播压缩快照（数组化，约 1~2KB/包）；客机不跑模拟，写入本地镜像并做部队航位推算（120px/s×两帧间隔） | 免除跨设备浮点确定性难题；PVE 的模拟核心零改动复用（`step` 只在主机调用） |
| 指令 | 客机派遣/卡牌 → `{t:'cmd'}` → 主机经 `Sim.command / cardPlay(owner=2)` 执行 → 下个快照回传结果 | 玩家与 AI、远程玩家共用同一命令接口的架构红利 |
| 视角 | UI 层以 `mySide`（1=主机 2=客机）替换全部 owner=1 硬编码：HUD/手牌 `hands[mySide]`/选中校验/派遣 owner/胜负 `over === mySide` | 同一份 UI 代码服务 PVE 与联机双方 |
| 模拟层 | `hands: {1:[],2:[]}` 双手牌，`cardPlay/canPlay` 增加 owner 参数（默认 1，PVE 行为不变） | 客机手牌由快照同步，出牌指令交主机结算 |
| 生命周期 | 房主暂停/继续广播；「再来一局」主机换种子重开并广播 `start`（双方 `createGame` 同种子 → 同图，城池 id/坐标天然对齐，快照无需传坐标）；断开即终止并弹「断·连」 | 最小状态机 |

已知边界：背景标签页 rAF 节流会延迟快照（回到前台即追平）；对称 NAT 下 STUN 直连可能失败（远期可加 TURN 或自建信令服务器）。

### 8.1 远期帧同步演进

若要 migrate 到帧同步：`sim` 已是固定步长 + 种子随机（`mulberry32` 仅用 `Math.imul/add/shift`，跨设备确定）+ 命令驱动——把「主机广播快照」替换为「双端交换带帧号的命令流 + 本地确定性重放」即可，浮点结算（`Math.sqrt` 为 IEEE 正确舍入）风险可控；届时再按需引入定点数。

## 9. 测试策略

| 层 | 工具 | 内容 |
|---|---|---|
| 逻辑 | `tools/verify-sim.js`（Node 无头） | 读取 inkwar.html，提取块1 执行，断言：地图生成约束 / 命令与结算不变量（驻军非负、易主后归属唯一、容量封顶、升级扣兵）/ 8 张卡效果数值 / 阵列散逸 / 胜负可达（AI vs AI 快进整局终有胜负）/ 困难 AI 显著强于容易 AI |
| 表现 | 浏览器实玩 + 渲染 PNG | 桌面/竖屏/横屏三布局、框选与瞄准交互、音效开关 |
| 视觉 | visual-judge（渲染 PNG 审查） | 布局完整性、对比度、遮挡、中文渲染 |

不变量（模拟任意时刻均需成立，逐帧断言抽样验证）：

1. 所有 `garrison/count ∈ [0, cap]` 且 ≥ 0；
2. 每座城池 `owner ∈ 0..4` 且易主瞬间墨量/统计只记一次；
3. `Army.count ≥ 1`（为 0 即销毁）；`Camp.count ≥ 1`（散逸至 1 为下限，不归零）；
4. 墨量 ∈ [0, 10]；手牌长度恒为 3（摸牌补偿即时）；
5. `over ≠ 0` 后 step 不再改变任何状态（幂等冻结）。
