## 1. 目的、范围与约定

### 1.1 目的

把「一个能双击打开就玩的回合制弹道对战游戏」拆成可验收的需求条目，使三件事可被独立判断：

1. **功能是否完整**——玩家从打开到通关的每一步，都有对应需求条目。
2. **质量是否达标**——响应式、触控、确定性、健壮性有可判定的约束，而不是主观描述。
3. **改动是否安全**——每条需求能反查到模块与验证组，改代码后知道该跑什么。

### 1.2 范围

**In Scope**

- 单人战役：15 关、3 章、3 档难度、顺序解锁
- 本地双人同屏：红蓝双方轮流操作，共用一台设备
- 回合制弹道对战：弹簧反向瞄准、抛射移动、12 种武器
- 可破坏像素地形：5 种材质、爆炸挖洞、结构坍塌
- 15 种道具与宝箱三通道供给（预置 / 空投 / 破坏掉落）
- 4 类关卡机关：迷雾、岩浆、雷暴、涨潮
- AI 对手：评分决策、弹道模拟、三档难度系数
- 本地存档与分档战绩
- 响应式三档布局（手机竖屏 / 手机横屏 / 桌面）与触控
- 程序化音频（18 个合成音效）
- 无头验证器与调试钩子

**Out of Scope（明确不做）**

| 不做项 | 原因 |
| --- | --- |
| 联网对战、房间匹配 | 单机定位；无服务端 |
| 账号体系、云存档 | 仅本地 `localStorage` |
| 关卡编辑器、地图导入 | 关卡为源码内数据表 |
| 行走 / 跳跃式移动 | 移动方式限定为「抛射自己」 |
| 内购、广告、体力 | 无商业化设计 |
| 多语言 | 仅简体中文 |
| 手柄、键位自定义 | 仅键鼠 + 触屏 |
| 录像回放、观战 | 无输入录制机制 |
| 原生 App 封装 | 交付形态为单 HTML |

### 1.3 需求陈述规范

1. **一条一行**：每条 FR 只描述一个可独立验收的行为，以「系统应……」陈述。
2. **可判定**：禁止「体验流畅」「界面友好」「性能良好」等无判据表述；确需定性时，必须附可观察判据或标注「未实测」。
3. **数值带常量名**：写 `MAXPOW=175` 而非「175」；写 `DEBRIS_MIN_PX=80` 而非「80 像素」。
4. **概率带条件**：概率型行为必须写明可控随机下的必然结果（`setRng(()=>0)` / `setRng(()=>0.999)`），不写「大约 xx%」。
5. **失败分支必写**：核心功能至少一条异常/边界描述（落水、预算耗尽、冷却中、存档损坏等）。
6. **同类合并**：12 种武器不写 12 条需求，写「1 条能力需求 + 1 张配置表」。

### 1.4 优先级定义

| 级别 | 含义 | 判定 |
| --- | --- | --- |
| **Must** | 缺失即不成立 | 去掉后游戏无法完成核心循环，或直接崩溃 |
| **Should** | 显著影响体验 | 缺失后仍可玩，但目标用户的核心诉求受损 |
| **Could** | 增强项 | 缺失不影响主路径，属打磨 |

版本归属沿用代码演进：v1 骨架 → v2 重写（44 断言）→ v3 弹簧 / 像素地形（65）→ v4 15 关 / 道具 / 宝箱（177）→ v5 响应式（229）。

### 1.5 编号体系

| 类型 | 形式 | 规则 |
| --- | --- | --- |
| 功能需求 | `FR-<域>.<序号>`，如 `FR-10.3` | 域固定 01–17；序号连续、永不复用；废弃保留 ID 并标「已废弃」 |
| 验收标准 | `AC-<域>.<序号>-<两位>`，如 `AC-10.3-01` | 每条 FR 至少 1 条 |
| 非功能需求 | `NFR-01` ~ `NFR-10` | 顺序号，不按域 |
| 用户画像 | `U1` ~ `U5` | 不随版本变化 |
| 使用场景 | `SC-01` ~ `SC-06` | 不随版本变化 |
| 架构模块 | `M01` ~ `M22` | 由 `ARCHITECTURE.md` 定义，本文只引用 |
| 架构决策 | `ADR-01` ~ `ADR-09` | 只在 `ARCHITECTURE.md` 定义 |
| 图 | `FIG-1` ~ `FIG-4` | 只在 `ARCHITECTURE.md` 定义 |

## 2. 产品概览

### 2.1 一句话定位

一款**零安装、零依赖、双击即玩**的回合制弹道对战游戏：玩家用反向拉弓把炸弹甩向敌方海盗，炸塌像素地形、抢空投宝箱，在 15 关三章战役中逐个击破 AI，或与身边的人同屏对战。

### 2.2 核心循环

```
选人 → 选工具 → 瞄准（反向拉弓） → 发射 / 抛射自己
   ↑                                    ↓
换边  ←  结算（投射物与飞行单位全部落地）  ←  爆炸 / 拾取 / 坍塌
```

一轮完整回合的可观察步骤：

1. 当前行动方选一名存活海盗（选中环出现，底部工具栏展开）。
2. 选择工具：`抛射移动` 或任一有弹药的武器。
3. 反向拖拽（弹簧被拉向反侧），虚线预览落点。
4. 松手发射；投射物飞行、碰撞、爆炸、改变地形。
5. 结算屏障等待所有投射物消失、所有飞行单位落地。
6. 若本回合是移动，行动方回到输入态，仍可再攻击一次；若是攻击，直接换边。
7. 任一方全灭即结算胜负；胜利解锁下一关。

### 2.3 内容规模基线

| 维度 | 规模 | 说明 |
| --- | --- | --- |
| 关卡 | 15 关 × 3 章 | 每章 5 关，地图宽 1600–2600 |
| 主题 | 10 种 | day / sunset / night / fog / volcano / storm / cave / tide / snow / abyss |
| 武器 | 12 种 | 3 种瞄准方式、9 种弹道行为 |
| 道具 | 15 种 | container 5 / buff 3 / tactic 3 / hazard 4 |
| 机关 | 4 类 | fog / magma / storm / tide |
| 难度 | 3 档 × 13 参数 | easy / normal / hard |
| 音效 | 18 个 | WebAudio 实时合成，无音频文件 |
| 角色 | 2 队（P/E） | 单队最多 3 人（含船长） |

### 3.2 画像详述

**U1 原作情怀玩家**

- 触发：看到「Mutiny 复刻」字样或朋友分享链接。
- 期待：反向拉弓的肌肉记忆、木箱与岩石被打穿的即时反馈、单位被炸飞后滑稽的翻滚。

- 关键需求：FR-01、FR-13、FR-14、FR-16。

**U3 同屏双人组合**

- 触发：两个人在一起，只有一台设备。
- 期待：红蓝配色一眼分辨；每回合开始有明确提示；不需要注册账号。
- 硬约束：回合归属有横幅提示；双方单位颜色固定（红 `#d8434e` / 蓝 `#3f7fd4`）；双人模式不依赖网络。
- 关键需求：FR-02.5、FR-03、FR-16.4。

**U4 通关挑战者**

- 触发：通关第一章后想继续。
- 期待：难度可选且真实生效；战绩能记录「哪关哪档赢了几次、最好几回合」；后期关卡有组合机关。
- 硬约束：三档难度参数全部接入（不是只改血量）；存档写入失败不崩溃。
- 关键需求：FR-02.2、FR-12.1、FR-13。

**U5 接手维护者**

- 触发：接需求改一个武器、加一关，或怀疑回归。
- 期待：知道改哪个函数、影响哪些模块、跑哪组断言。
- 硬约束：模块表覆盖全部行号；每条需求能反查验证组；概率机制可用固定种子复现。
- 关键需求：FR-17、NFR-06、NFR-10。

## 4. 核心使用场景

### 4.1 场景模板

每条场景固定八个字段，避免写成「用户打开游戏然后玩」这种无法验收的叙述：

```
SC-xx 标题
- 角色：U?（可复合）
- 触发情境：什么设备、什么时机、为什么打开
- 目标：用户可感知的完成状态
- 前置条件：进度 / 难度 / 关卡 / 阶段状态
- 主路径：编号步骤，每步写「操作 → 系统反馈」
- 异常分支：失败、误操作、环境异常，以及系统如何兜底
- 成功判据：可观察、可验收的结果
- 关联需求：FR-xx.y / NFR-xx
```

### 4.2 场景卡

#### SC-01 手机竖屏首次开火

- **角色**：U2
- **触发情境**：通勤路上，微信里点开链接，手机竖屏单手持机。
- **目标**：30 秒内完成第一次发射并看到爆炸。
- **前置条件**：无存档或仅解锁第 1 关；`screen=menu`。
- **主路径**：
  1. 打开页面 → 直接进入主菜单，甲板上有海盗剪影与四个按钮。
  2. 点「☠ 单人闯关」→ 进入难度选择。
  3. 点「普通」→ 加载第 1 关，出现「第 1 回合」横幅。
  4. 点己方海盗 → 选中环出现，底部工具栏展开（每格 ≥44px）。
  5. 点「🍒 樱桃炸弹」→ 进入瞄准态。
  6. 在海盗身上向反方向拖拽 → 虚线预览反向弹道与落点。
  7. 松手 → 投射物飞出、命中爆炸、地形留焦痕。
  8. 结算完成 → 换到敌方回合，横幅提示「敌军行动…」。
- **异常分支**：
  - 拖拽距离 < 8 CSS px → 判定为点按，不发射，保持选中态。
  - 拖拽到空白处 → 不改变镜头（只有 `panning` 态才平移），不会误移画面。
  - 竖屏高度不足以放下工具栏 → 工具栏上移，绝不被裁切（`toolbarH=126+si.b`）。
- **成功判据**：出现至少一次爆炸特效；`phase` 从 `resolve` 回到 `input` 或切到 `ai`；无控制台异常。
- **关联需求**：FR-01.1、FR-05.1、FR-14.1、FR-14.4、FR-14.7、FR-14.8

#### SC-02 桌面连续通关

- **角色**：U1、U4
- **触发情境**：周末在电脑前，准备一次打通前三关。
- **目标**：通关第 N 关并解锁第 N+1 关，刷新最佳回合。
- **前置条件**：`unlocked ≥ N`；`screen=levels`；已选难度。
- **主路径**：
  1. 主菜单点「📜 选择关卡」→ 15 张卡片按 3 章分组展示，已解锁关卡高亮。
  2. 点第 N 关 → 进入难度选择，三档卡片显示该档最佳回合。
  3. 点「普通」→ 加载关卡，敌方血量按 `hpMul=1.00` 生成。
  4. 循环「选人 → 拉弓 → 结算 → 换边」，直至敌方全灭。
  5. 出现胜利页，显示回合数与「下一关」按钮。
  6. 点「下一关」→ 直接以同难度进入第 N+1 关。
- **异常分支**：
  - 己方全灭 → 失败页，提供「重试 / 选关 / 主菜单」。
  - 浏览器禁用 localStorage → `save()` 静默失败，本次会话仍可继续，刷新后回到旧进度。
  - 投射物卡住 → 30 秒熔断强制清场并结束回合。
- **成功判据**：`G.unlocked` 增加 1；`records[N][难度].win` 增加 1、`best` 取 `min(旧值, G.turns)`；刷新页面后进度仍在。
- **关联需求**：FR-02.1、FR-02.2、FR-02.4、FR-03.2、FR-03.3、FR-13.4

#### SC-03 跨沟抢空投

- **角色**：U2、U3
- **触发情境**：第 5 关之后地图变宽，空投落在 600 世界单位外的对岸，没有「走路」这种移动方式。
- **目标**：在不结束回合的前提下拿到宝箱，并且本回合仍能发射一次武器。
- **前置条件**：`screen=play`、`phase=input`、当前单位 `movesUsed=0`、空投已落地。
- **主路径**：
  1. 点选己方海盗 → 出现选中环。
  2. 选「🚀 抛射移动」→ 进入 `drag` 瞄准。
  3. 在海盗身上向反方向拖拽 → 虚线预览反向抛物线。
  4. 松手 → `throwSelf` 把单位设为飞行态，`phase=resolve`、`resolveKind='move'`。
  5. 落地 → `pickupNearby` 自动拾取半径内道具。
  6. 结算完成 → 回到 `input`，`movesUsed=1`。
  7. 再选武器发射 → `resolveKind='attack'` → 换边。
- **异常分支**：
  - 力度 < 14 → 视为取消，不消耗移动次数。
  - 落水 → `killUnit(drown)`，可能导致直接判负。
  - 移动次数已用完 → 工具栏的「抛射移动」置灰或不出现。
  - 落点悬空 → 单位继续下落，直至落地或落水。
- **成功判据**：道具被拾取（进入背包或立即生效）；`phase` 回到 `input` 且 `movesUsed=1`；随后一次攻击能正常结算并换边。
- **关联需求**：FR-04.5、FR-05.4、FR-05.7、FR-09.3、FR-10.1

#### SC-04 炸塌结构制造落水

- **角色**：U1、U4
- **触发情境**：敌人站在木质平台或独立岩柱上，直接命中伤害不足。
- **目标**：炸掉支撑结构，让敌人悬空坠落并落水，同时触发破坏掉落。
- **前置条件**：持有 `dyn`（炸药）或 `cherry`；目标下方为可破坏材质。
- **主路径**：
  1. 选中海盗，选「🧨 炸药」。
  2. 反向拉弓，使落点位于支撑结构底部。
  3. 松手 → 投射物弹跳两次后爆炸。
  4. `explode` 调用 `Terrain.cut` 挖洞 → 单位脚下失去支撑。
  5. `update` 中单位悬空 → 进入下落 → 落水 → 水花 + 死亡音。
  6. `maybeDebris` 依据被清除像素的材质统计决定是否生成掉落物。
- **异常分支**：
  - 破坏量 < `DEBRIS_MIN_PX=80` → 不算「炸塌」，不进入掉落判定。
  - 处于 `DEBRIS_COOLDOWN=0.6` 秒冷却内 → 本次不掉落。
  - 场上掉落物已达 `DEBRIS_MAX_FIELD=6` → 不再生成。
  - 殉爆链深度达 `DEBRIS_MAX_DEPTH=3` → 停止递归。
  - 关卡 `debrisBudget` 耗尽 → 本回合不再掉落。
- **成功判据**：目标单位落水死亡；若满足门控，场上新增至少 1 个道具且其 `src='debris'`。
- **关联需求**：FR-07.1、FR-07.3、FR-07.6、FR-10.6、FR-10.7

#### SC-05 同屏双人一轮

- **角色**：U3
- **触发情境**：两个人只有一台笔记本，想轮流玩一局。
- **目标**：完成红方移动 + 攻击、蓝方移动 + 攻击的一轮交替，并能判定胜负。
- **前置条件**：主菜单选「⚔ 双人对战」；`mode='2p'`。
- **主路径**：
  1. 选关与难度 → 进入对局。
  2. 横幅提示「红方 行动！」→ 红方选中己方海盗。
  3. 红方拉弓发射 → 结算 → 横幅切换「蓝方 行动！」。
  4. 蓝方重复同样流程 → 结算 → 回到红方。
  5. 任一方全灭 → 胜利/失败页。
- **异常分支**：
  - 2P 下没有 AI 回合，`phase` 始终由 `input` 驱动。
  - 观战方误触 → 只能操作当前 `turnTeam` 的单位，选中他人单位无效。
  - 双人模式下的胜利也会写入战绩（当前实现），需在验收时确认是否符合预期。
- **成功判据**：两次换边顺序正确；横幅队伍名与实际可操作单位一致；全灭后进入结算页。
- **关联需求**：FR-02.5、FR-03.1、FR-16.4

- **关联需求**：FR-02.4、FR-12.1、FR-13.3、FR-17.1、NFR-10

## 8. 验收与验证策略

### 8.1 验收标准写法

一条 AC 必须能回答四个问题：**在什么状态（给定）→ 做什么（当）→ 观察到什么（则）→ 由谁证明（验证）**。

```
AC-05.1-01 | 单位在 (100,300)，武器 cherry | 在 (100,400) 松手 | 投射物初速方向向上，模长 = 100×POW2V | [4]
```

七条编写原则：

1. **按组映射，不复制断言文案**——AC 只登记「验证组号 + 支撑的可观察量」，断言改名不影响 AC。
2. **每条 FR 至少一条 AC**，并标注验证方式：`自动 [n]` / `人工` / `审查` / `未覆盖`。
3. **数值必须带常量名**（`MAXPOW`、`DEBRIS_MIN_PX`、`resolveWait`），禁止裸数字。
4. **概率型 AC 必须写明可控随机**（`setRng(()=>0)` 必然、`()=>0.999` 必然不发生）。
5. **核心 FR 至少一条失败分支**（落水、预算耗尽、冷却、存档损坏、采样失败）。
6. **断言总数只在文档基线出现一次**（229 / 21），不在各域累加。
7. **组号变更只改两处**（§8.2 与本文件附录 C），不改 FR 正文。

### 8.3 覆盖形态定义

| 形态 | 含义 | 使用场景 |
| --- | --- | --- |
| **自动** | 有对应断言，可一条命令复跑 | 逻辑、数值、边界、布局几何 |
| **人工** | 需在浏览器中按步骤观察 | 手感、视觉、真实触屏、音频 |
| **审查** | 代码可判定，但暂无自动断言 | 常量表完整性、分支存在性 |

### 8.4 覆盖缺口

| 缺口 | 原因 | 建议 |
| --- | --- | --- |
| FR-15 音频全部 | 无头环境无 AudioContext | 真机听感验收；可在 mock 中至少断言音效键存在 |
